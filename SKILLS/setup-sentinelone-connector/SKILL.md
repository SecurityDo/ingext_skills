# Set up the SentinelOne API connector

Import **SentinelOne EDR** activity and threat events into Fluency / Ingext via the SentinelOne
management API. Two things are needed, and only one of them is yours to collect from the
customer:

- **SentinelOne side (customer's management console):** an **API token**, generated by a user
  (or, better, a service user) whose role's permissions the token inherits. Portal-only —
  guide it, step by step.
- **Fluency side (yours):** install the **`SentinelOneAPI`** connector (display name
  "SentinelOne API") with the console base URL and that token. Do this for the operator via the
  MCP.

> **Sourcing note:** SentinelOne's own product documentation sits behind a customer login. The
> vendor-side steps below are verified against major SIEM vendors' published integration guides
> (Elastic, Microsoft Sentinel, Sumo Logic) — cited as **secondary sources** in
> `assets/references.md`.

> **Variant check:** the live template list also carries a sibling **`SentinelOne`** template
> ("SentinelOne API Integration" — activity/threats **plus alerts and resource dump**). This
> skill installs **`SentinelOneAPI`**. If the operator explicitly wants the extended variant,
> the vendor-side runbook here still applies, but do the install through `add-connector`
> against that template instead.

## What this creates

| Side | Item | Detail |
|---|---|---|
| SentinelOne | (Recommended) a dedicated service user | Least-privilege token owner with view permissions on the data the connector reads |
| SentinelOne | API token | Value shown **once**; inherits the owner's role permissions; **expiry varies by token type** — record the expiry date the console shows at generation |
| Ingext | Connector | Template **`SentinelOneAPI`** ("SentinelOne API"), instance e.g. `sentineloneapi`, datalake index default `SentinelOne` |

Nothing here is billable on the SentinelOne side.

## Prerequisites

- A **SentinelOne console administrator** who can create users/service users and generate API
  tokens (Microsoft Sentinel's integration guide has the admin create the API user with the
  **Admin** role; a scoped-down role works if it keeps the view permissions listed below).
- The **console base URL** — the tenant URL the customer signs in at, e.g.
  `https://<tenant>.sentinelone.net`.
- The **Fluency Ingext MCP** connected for the target Ingext instance. Without it, the operator
  pastes the values into the Fluency UI instead.

## The offer — who does what

The SentinelOne management console cannot be driven by the agent — an S1 admin clicks those
steps. Ask (use `AskUserQuestion` if unclear) whether the operator wants:

- **(a) Guided + agent installs (default):** you walk the admin through the token creation
  click-by-click, collect the two values (console base URL, API token), and then **you** create
  the Ingext connector and verify ingestion.
- **(b) Runbook only:** print the full procedure (both sides) for the customer to run later —
  e.g. when the S1 admin isn't in this conversation. Offer to resume the install step whenever
  they return with the values.

If the operator already has a working console URL and API token in hand, skip straight to the
[Ingext-side install](#ingext-side--install-the-connector).

## SentinelOne side — create the API token (guided)

### 1 — Pick the token owner (least privilege)

A SentinelOne API token **inherits the permissions of the user who generates it**. The
connector reads EDR activity and threats, so per Elastic's published permission map the owner's
role needs at least: **Activity → view**, **Endpoints → view**, and **Threats → view**.

- **Recommended:** a dedicated **service user** (Settings → Users → Service Users in consoles
  that offer them) — it has no interactive login to protect, and its token duration is chosen
  at creation. Scope it to the site(s)/account the customer wants ingested.
- **Acceptable for a quick start:** an existing console user generates the token (Microsoft
  Sentinel's guide simply creates a new console user with the **Admin** role). Note in your
  report that the integration is then tied to that account and over-privileged.
- **UNVERIFIED:** the exact name of the least-privilege *built-in* role in the customer's
  console (S1 role names vary by console version and are documented behind login). Have the
  admin check Settings → Users → Roles for a view-only role covering the permissions above, or
  obtain the current recommendation from SentinelOne documentation/support.

### 2 — Generate the token

In the **SentinelOne management console** (paths per the cited secondary sources; console
versions vary slightly):

- **Console user:** top-right account menu → **My User** → **Actions → API Token Operations →
  Generate API Token** (labelled "API Token Operators" in some versions). Enter the MFA code if
  prompted.
- **Service user:** **Settings → Users → Service Users → Actions → Create New Service User** —
  choose the scope and expiration; the token is presented on creation.

**Copy or download the token immediately** — it is shown **once**. This is the connector's
`APIToken` parameter. Note that regenerating a user's token invalidates the value the connector
holds — coordinate rotation, don't regenerate casually.

> **Token lifetime — honest answer:** published sources disagree, likely reflecting token type
> and console version. Elastic documents a **30-day default for console-user tokens** and
> "duration chosen at creation" for service users; other integration vendors (runZero,
> NinjaOne) document **six-month** expiry. **Treat the expiry date the console displays at
> generation as the truth**, record it, and put the rotation on a calendar — ingestion stops
> silently when the token lapses (see Failure modes).

### 3 — Collect the console base URL

The connector's `URL` parameter is the **management console base URL** — the address the
customer signs in at, e.g. `https://usea1.sentinelone.net` (format
`https://<tenant>.sentinelone.net`). Supply the scheme and host only — no trailing path.

**Deliverables from this section:** `URL` + `APIToken` (the token is a credential — never echo
it back; refer to it as "the API token from step 2").

## Ingext side — install the connector

With the two values in hand, do this for the operator (MCP connected):

1. **`list_connector_templates`** — locate the live **`SentinelOneAPI`** template ("SentinelOne
   API") and use its current parameter schema; the names below are a snapshot, not truth. (Mind
   the sibling `SentinelOne` template — see the variant check above.)
2. **`list_connectors`** — if a SentinelOne connector already exists, show its instance/state
   and confirm before adding a second instance.
3. **`create_connector`** with:
   - `application`: `SentinelOneAPI`
   - `instance`: `sentineloneapi` (lowercase, ≤20 chars, **never `"default"`**; `-2` suffix on
     collision)
   - `displayName`: `SentinelOne API`
   - `inputParameters`: **every** template parameter — `URL`, `APIToken` (sensitive), and the
     defaulted `datalake` (`managed`) / `index` (`SentinelOne`) unless the operator wants
     otherwise.
4. Confirm the instance exists and reports healthy (`list_connectors` / `get_connector`).

**Without the MCP:** walk the operator through the Fluency UI — Connectors → Add →
**SentinelOne API**, paste the console URL and token, save.

## When called from `customer-onboarding`

- **This skill is the complete stage — connector included.** Do **not** hand off to
  `add-connector`; run the install section above before returning.
- **Don't re-collect** what the router already established (connected instance, existing
  connectors from its `list_connectors` call).
- **Hand back** for the router's checklist and verification: the connector `instance` id and
  the datalake index (default `SentinelOne`; confirm the live table name with
  `list_data_tables`). Do not echo the API token anywhere in the summary.
- **Latency expectation:** the connector polls the SentinelOne API; first events should land
  within roughly **15–30 minutes**. Activity events flow steadily in any live fleet, but threat
  events are sparse in a healthy one — compare with the console's own Activity view before
  calling it broken. Mark ⏳ inside that window, not ❌.

## Verification

1. `list_connectors` / `get_connector` — instance present, no error state.
2. After ~15–30 min, count rows in the `SentinelOne` datalake index over the last hour via the
   **`ingext-kql`** skill (confirm the live table name with `list_data_tables` first). A plain
   row count is the smoke test.
3. Cross-check against the customer's own console **Activity** view — if it shows events for
   the same window and the datalake shows none past the latency window, move to Failure modes.

## Failure modes

| Situation | Response |
|---|---|
| Connector errors with 401 / invalid token | Token was mistyped, expired (check the date recorded at generation — defaults vary from 30 days to six months by token type), regenerated by someone (which invalidates the old value), or its owner was deactivated. Generate a fresh token (step 2) and update the connector. |
| Wrong URL | Must be the console base URL with scheme, e.g. `https://usea1.sentinelone.net` — no trailing path, not a regional API alias the customer guessed. Use exactly what the browser shows when signed in to the console. |
| 403 / permission errors on some data | The token inherits the owner's role. Ensure the role has Activity → view, Endpoints → view, and Threats → view (per the cited permission map), and that the owner's scope covers the intended sites. |
| Events flowed, then stopped | Almost always token expiry (silent) — regenerate and update the connector. Otherwise check whether the owner was deactivated or descoped. |
| Token value not captured | Shown once. Generate a new token (which replaces the lost one) and use that. |
| A SentinelOne connector already exists | Ask before adding a second instance (`sentineloneapi-2`); two instances polling the same console double the API load for no benefit unless they intentionally target different datalake indexes. |
| Customer wanted the extended variant | The sibling `SentinelOne` template ("SentinelOne API Integration", with alerts + resource dump) is a different connector — same credential works; install it via `add-connector`. |
| Customer actually means Microsoft Sentinel | Unrelated product despite the name — return to `customer-onboarding` / the catalog. |

## Security notes

- The API token is a credential: never paste it into logs, tickets, summaries, or long-lived
  chat beyond the `create_connector` call.
- **Least privilege lives in the owner's role** — S1 tokens have no scoping of their own, so a
  service user with view-only permissions on Activity/Endpoints/Threats is the control.
- Rotation: generate the new token, update the connector, and treat the old value as dead (a
  user's regenerated token replaces the previous one). Rotate immediately if the token is ever
  exposed.
- Expiry is enforced but not loudly announced — record the expiry date at generation and put
  the rotation on a calendar rather than waiting for ingestion to stop.
- Deactivating the owning account invalidates the token — plan for this when admins offboard;
  another reason the owner should be a service user.
