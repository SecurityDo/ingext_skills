# Set up a generic HEC passthrough intake

Bring in logs from a product the platform has **no dedicated connector for**, using the one
protocol almost every security product can speak: **Splunk-compatible HTTP Event Collector
(HEC)**. Two halves, and only one belongs to the customer:

- **Fluency side (yours):** install the **`HecPassthrough`** connector (display name "HEC
  Input Passthrough"). Installation **generates** the two values the source needs — a HEC
  **`url`** and a HEC **`token`** (the template's `output` block).
- **Source side (customer's product):** point the product's Splunk/HEC-compatible output at
  that url + token. This skill's guidance here is generic by design — the product has no
  template, so it has no product-specific runbook; the protocol steps are backed by Splunk's
  HEC documentation (citations in `assets/references.md`).

> **Install first, then configure the source.** Unlike API-polling connectors, the
> credential flows *out of* the install: `create_connector` is what mints the url + token, so
> the Fluency side always happens before the vendor side.

## What this creates

| Side | Item | Detail |
|---|---|---|
| Ingext | Connector | Template **`HecPassthrough`** ("HEC Input Passthrough"), instance e.g. `hecpassthrough` |
| Ingext | Datalake index | The `index` parameter — **override the `default` default with a source-derived name** (see below) |
| Ingext | HEC url + token | Generated by the install (template `output` block). The **token is a credential** |
| Source | Output config | The customer's product configured to send to that url with that token — nothing is created on the vendor side by this skill |

Nothing here is billable on the vendor side.

---

## Prerequisites

- The source product must have a **Splunk-HEC-compatible output** (often called "Splunk",
  "HEC", or "HTTP Event Collector" in its export/SIEM settings) and be able to reach the
  Fluency HEC endpoint over HTTPS.
- Someone with **admin access to the source product** to paste the url + token into its
  output settings.
- The **Fluency Ingext MCP** connected for the target Ingext instance. Without it, the
  operator installs via the Fluency UI and reads the url + token there instead.

## Step 0 — make sure this is really the right skill

`HecPassthrough` is the **fallback of last resort**. Call `list_connector_templates` (live)
and check whether the product actually has its own template:

- A **dedicated HEC template** exists for Bitdefender Security Telemetry (`BitdefenderST` —
  route to `setup-bitdefender-securitytelemetry-connector`), Zscaler NSS (`Zscaler`), and
  Coro (`CoroHEC`) — prefer those (via `add-connector` where no dedicated skill exists yet):
  they land rows in properly named tables with the right parsers.
- Any **other dedicated template** (API, syslog, …) for the product also wins over a generic
  passthrough.

Only when the live list has nothing for the product does this skill proceed.

---

## Step 1 — name the index after the source

Ask **what will be sending** (product name, e.g. pfSense, some NDR appliance, a custom app).
Then pick the datalake `index`:

- **Recommend overriding the template's `default` index with a source-derived name**, e.g.
  `PfSense` — a short alphanumeric name the customer will recognize.
- **Why it matters:** (1) *table hygiene* — every HEC passthrough writing to `default` piles
  unrelated products into one mixed table; a per-source index gives each product its own
  datalake table; (2) *later querying* — KQL, reports, and verification all address the table
  by name, and `PfSense` is discoverable where `default` is a junk drawer. It also keeps a
  second passthrough for a different product cleanly separated.
- Keep `datalake` at its default (`managed`) unless the operator says otherwise.

---

## Step 2 — install the connector

With the MCP connected, do this for the operator:

1. **`list_connector_templates`** — locate the live **`HecPassthrough`** template ("HEC Input
   Passthrough") and use its current parameter schema; the names here are a snapshot, not
   truth.
2. **`list_connectors`** — if a HecPassthrough instance already exists, show its
   instance/state and confirm before adding another (a second source gets its **own**
   instance + index; don't share one token across products).
3. **`create_connector`** with:
   - `application`: `HecPassthrough`
   - `instance`: `hecpassthrough` (lowercase from the template name, ≤20 chars, **never
     `"default"`**; `-2` suffix on collision — e.g. a second source's passthrough)
   - `displayName`: `HEC Input Passthrough <Source>` (e.g. `HEC Input Passthrough PfSense`) so
     the instance's purpose is obvious
   - `inputParameters`: **every** template parameter — `datalake` (`managed`) and `index`
     (the source-derived name from Step 1).
4. Confirm the instance exists and reports healthy (`list_connectors` / `get_connector`).

**Without the MCP:** walk the operator through the Fluency UI — Connectors → Add → **HEC
Input Passthrough**, set the index, save.

---

## Step 3 — capture the output: the HEC url + token

The template has an **`output` block**: after install, the platform generates and exposes
**`url`** (HEC Server URL) and **`token`** (HEC Security Token). Retrieve them
(`get_connector` on the new instance, or the connector's page in the Fluency UI) and hand
both to the operator **once** — this hand-off is the whole point of the install.

> **The token is a credential.** Hand it to the person configuring the source and stop —
> never repeat it into summaries, checklists, tickets, or the onboarding hand-back. Refer to
> it as "the HEC token from the install".

---

## Step 4 — point the source at it (generic guidance)

In the product's Splunk/HEC output settings:

1. **URL:** paste the returned `url` **exactly as returned**. Do not invent or append path
   segments (Splunk's own servers use `/services/collector/event`, but the Fluency endpoint's
   exact shape is whatever the platform returned — the returned value is the complete truth).
   If the product asks for host/port/path as separate fields, split the returned url into
   those parts without adding anything.
2. **Token:** paste the returned `token` where the product asks for the HEC/Splunk token.
   Products implementing the protocol themselves send it as the documented HEC auth header:
   `Authorization: Splunk <token>` (see references).
3. **Event format:** products with a native Splunk/HEC output already speak the protocol —
   JSON envelopes with the event payload under the `"event"` key, optional `time` / `host` /
   `source` / `sourcetype` metadata keys (see references). Nothing to hand-craft unless the
   customer is scripting a custom sender.

**Smoke test** (from any machine that can reach the endpoint — use the returned url
verbatim):

```bash
curl -H "Authorization: Splunk <token from step 3>" \
     -d '{"event": "ingext hec passthrough smoke test"}' \
     "<url exactly as returned in step 3>"
```

A 2xx response means the endpoint accepted the event; give it a couple of minutes, then count
rows in the index (Verification below). (The `Authorization: Splunk <token>` header and the
`"event"`-key JSON envelope are the documented HEC protocol — citations in
`assets/references.md`. The response body's exact shape from the Fluency endpoint is not
documented here; judge by the HTTP status plus the row count.)

## When called from `customer-onboarding`

- **This skill is the complete stage — connector included.** Do **not** hand off to
  `add-connector`; run the install above before returning.
- **Don't re-collect** what the router already established (connected instance, existing
  connectors from its `list_connectors` call).
- **Hand back** for the router's checklist: the connector `instance` id and the chosen
  datalake index (confirm the live table name with `list_data_tables`), plus a note that the
  url + token were delivered to the operator for the source-side config. **The token never
  appears in the hand-back.**
- **Zero rows is the expected state** until the customer actually configures the source and
  it starts pushing — HEC is push, not poll; nothing arrives on its own. The router should
  mark the application **⏳ with the source-side follow-up noted, not ❌**. Once the source
  pushes (or the smoke-test curl fires), rows should appear within a couple of minutes.

---

## Output — the deliverable

Report human-readably plus a JSON block a calling task can parse. The url is included (it is
not marked sensitive in the template); **the token is not**:

```json
{
  "connector": "HecPassthrough",
  "instance": "hecpassthrough",
  "index": "PfSense",
  "source": "pfSense",
  "hecUrl": "<url as returned by the install>",
  "tokenDelivered": true
}
```

---

## Verification

1. `list_connectors` / `get_connector` — instance present, no error state.
2. **Fire the smoke-test curl** (Step 4) if the source isn't configured yet — it proves the
   endpoint + token independently of the vendor side.
3. Count rows in the chosen index over the last hour via the **`ingext-kql`** skill (confirm
   the live table name with `list_data_tables` first — the index parameter is the strong hint,
   but confirm rather than trust). A plain row count is the smoke test.
4. **Honest latency:** nothing arrives until the source pushes — zero rows before the
   source-side config is finished is correct, not a failure. After the source (or the curl)
   sends, expect rows within a couple of minutes.

## Failure modes

| Situation | Response |
|---|---|
| Smoke-test curl gets 401/403 | Wrong or truncated token. Re-read it from the connector (`get_connector` / the UI) and re-paste — it is re-retrievable, unlike an AWS secret. |
| Curl gets 404 / connection error | The url was altered — a path segment added or a host mangled. Use the returned url **verbatim**; check outbound HTTPS from the sending network. |
| Source configured but zero rows after several minutes | Run the smoke-test curl. Curl works → the source isn't actually sending (check its own export logs, TLS trust, egress firewall). Curl fails too → endpoint/token problem, previous rows. |
| Rows landing but under a wrong/`default` table | The index was left at `default` or mistyped at install. Create a replacement instance with the right index (and retire the old one) — then re-point the source at the new url + token. |
| Product turns out to have its own template | Step 0 was skipped. Prefer the dedicated template/skill — install it and retire the passthrough instance, so parsing and table naming are correct. |
| A HecPassthrough instance already exists | One instance per source. Add `hecpassthrough-2` (its own index + token) for a new product rather than sharing tokens across products. |
| Token exposed (pasted into a ticket, repo, …) | Treat as compromised — anyone with url + token can inject events into the datalake. UNVERIFIED: whether the platform can rotate a HEC token in place — absent that, create a replacement instance (new token), re-point the source, then delete the exposed instance. |
| Template renamed / schema drift | The install step reads the live `list_connector_templates` — follow the live schema, not this file's snapshot. |

## Security notes

- **The HEC token is a bearer credential**: possession of url + token is sufficient to inject
  arbitrary events into the customer's datalake. Store it only in the source product's
  configuration (its secret store if it has one); never in logs, tickets, summaries, or chat
  beyond the single hand-off.
- The url alone is less sensitive but still names an ingestion door — no need to publish it
  beyond the people configuring sources.
- **Rotation / revocation:** UNVERIFIED whether an in-place token rotation exists on the
  platform — the reliable path is create a new instance (which mints a fresh token), re-point
  the source, delete the old instance. Do this on any suspected exposure and when a source is
  retired, so no orphaned token stays valid.
- **One instance per source product.** Sharing one token across products merges their rows
  into one table and makes revocation all-or-nothing.
