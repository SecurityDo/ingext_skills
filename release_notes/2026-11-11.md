# 2026-11-11 — ingext-kql 1.1.5 → 1.1.6

Schema resync: Okta System Log events are now in the knowledge base, plus a self-join warning.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| ingext-kql | 1.1.6 | released |

## What changed

- New stream table: `Okta` (21 fields, 6 example queries), from `ingext_schema`
  `datatypes/Okta/`. Dynamic JSON (root `@okta`), fields referenced bare; `timestamp` equals
  `published`.
  - The schema warns about six traps. One sign-in is several records sharing
    `authenticationContext.externalSessionId`, so logins are counted on `user.session.start`.
    `client.ipAddress` can be a back end signing users in on their behalf. `VERIFICATION_ERROR`
    means the username does not exist, not a wrong password. Empty values are literal strings
    (`"null"`, `"unknown"`). Okta's risk and behavior verdicts should be read from
    `securityContext`, not the map strings in `debugData`. Self-joins need a `let` per side.
  - The example queries cover: unknown-user spraying from one IP, successful sign-ins by
    scripting clients, sign-ins Okta flagged as new country and new ASN, three or more users
    signing in from one IP within a minute, a user's sessions with the apps they opened, and
    security-relevant admin changes.
- **SKILL.md:** the join note now says self-joins must bind each side to a `let`. An inline
  same-table right side returns nothing after a `summarize` and undercounts before one, with no
  error (engine bug; fix pending).
- No other table changed. `--check` passes against `ingext_schema` (51 tables).
  `cowork/ingext-kql.skill` rebuilt.

# 2026-11-11 — incident-investigation 1.6.8 → 1.6.9

The Okta workflow reads successful sign-ins, the client behind each one, and what each session reached, not only failures.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.6.9 | released |

## What changed

- **`references/workflows/okta.md`:**
  - Reads the client before the address. A back end (`Java/...`, `LdapAsAService`) signs users in
    on their behalf. A scripting client (`Go-http-client`, `python-requests`, `curl`) is a tool.
    The Okta sign-in page has its own widget header, and a browser user agent without it is weak
    on its own. The queries print this as `clientType`.
  - A second pattern next to the legacy spray: a valid password used by a tool.
  - K2 starts from the successes: the subject's sessions with their factor, the apps they opened
    and Okta's own new-behavior verdict, plus the same client or address on other accounts
    tenant-wide.
  - K3 separates usernames that do not exist (`VERIFICATION_ERROR` / `UNKNOWN_USER`) from real
    accounts.
  - K5 counts MFA from `auth_via_mfa` or a factored `verify`, which is how Identity Engine
    records it, and reads a shared address both ways: office egress, or one tool working
    through accounts.
  - Engine notes: both field forms work. A same-table join or union leg after the first
    `summarize`/`top`/`take`/`distinct`/`count` is refused, so bind it to a `let`. A `truncated`
    result has lost groups. Don't name a computed column after a field root (`client`,
    `actor`...). The 30-day windows end at `{WTO}`, not at the time of the run.
- **New queries:**
  - `okta_sessions`: one row per session, from sign-in to apps, with `mfa` and `positive`
    behaviors.
  - `okta_tenant_signins`: scripting-client sign-ins over 14 days, and 3+ users in one minute
    from an address over 2 days.
  - `okta_unknown_user_spray`: unknown usernames by address; tools first.
- **Changed queries:**
  - `okta_auth_paths`: `scripted`, `clients` and a `blocked app access` path.
  - `okta_auth_events`: sign-on policy, OAuth and blocked-app events, plus the widget, factor,
    app and ASN.
  - `okta_attacker_ips`: the clients behind each address.
  - `okta_ip_users`: clients, `peakPerMin` and days, in one pass with no `let`.
  - `okta_success_profile`: per-client rows; MFA from either factor event.
  - `okta_spray_census` and `okta_shared_ips`: real accounts vs unknown names.
  - Every 30-day window is anchored on the incident.
- Tested on a live Okta Classic tenant: a password-only takeover of four shared accounts by a
  scripted client from two hosting networks, followed by a browser sign-in, surfaces in
  `okta_tenant_signins`, `okta_sessions`, `okta_auth_paths` and `okta_ip_users`.
- `cowork/incident-investigation.skill` rebuilt.
