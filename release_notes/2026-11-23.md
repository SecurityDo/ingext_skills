## What changed

- **New example `references/examples/fork.md`:** one read of the table feeds several
  subqueries in parallel, and the response has one table per subquery. It covers naming
  (`Name = (...)`, a trailing `| as Name`, or `Fork_1`, `Fork_2`), a fork after a `summarize`,
  the rules (`fork` is the last operator; a subquery cannot hold `join`, `union`, `facet` or
  another `fork`; `kql_summary` refuses it), `fork` against `facet`, and the same answers as
  separate queries.
- **SKILL.md:** a `fork` note in KQL basics, and step 3 points to the example.
- **`references/kql_syntax.md`:** a short `fork` section.
- Every query in the example was run on two tenants on lake 2.10.25. Each fork table matched the
  same subquery run on its own. Over 90 days of Office 365, four summarizes took 4.8 s as one
  fork against 18.2 s as four queries.
- No schema change. `cowork/ingext-kql.skill` rebuilt.
