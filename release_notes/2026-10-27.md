# 2026-10-27 — CISO_monthly_report 1.0.0 (new)

| Skill | Version | Status |
| --- | --- | --- |
| CISO_monthly_report | 1.0.0 | released |

**The monthly SOC story for one tenant, for a CISO.** One self-contained HTML report with 8 chapters
and 16 sections: an executive summary with a Green, Amber or Red rating and at most two decisions,
what happened, repeat patterns and root-cause themes, coverage and blind spots, attack pathways and a
risk register, response performance, a NIST SP 800-53 evidence add-on, a remediation plan, client
actions and an appendix.

- **Inputs:** the tenant's own MCP connector: `behavior_summary_search` (cases for the month and the
  prior month, with their comments), the health-status-report evaluation (installed-application status and
  resource-feed ages), `get_azure_user_record` (administrator roles of repeat users) and the
  compliance-assessment results.
- **Events to escalation:** section 2 shows events written to the datalake (a PromQL ingest counter), tickets
  flagged at 3,000 or more, tickets the AI assistant ran on, closed, and escalated (still new after the AI
  ran). Tickets below 3,000 are not counted.
- **Reused, not repeated:** O365 hygiene, environment changes and vulnerability rows, and which repeat
  actors are administrators, come from the facts compliance-assessment already collected.
- **Computed locally:** case shapes (rule combinations), repeat actors, response and close times,
  and who responded: the automated assistant or an analyst.
- **Data integrity:** `scripts/build_report.py` computes every figure, table, chart, risk score and
  band from the saved tool results. The analyst writes only the narrative, which refers to computed
  values with placeholders; any other number in it is listed as a warning to check.
- **Contract enforced:** chapters 2 to 7 need analysis of at least 150 words, one to three finding
  callouts, one graphic and one table; remediation actions need calendar due dates.
- **Marked, never filled in:** the SOC escalation log, the SOC change log, control effectiveness, the
  alerts-processed denominator, and any prior-month figure without a prior-month pull show as GAP or
  PARTIAL. The risk register is analyst-scored and flagged PARTIAL.
- **Wording:** compliance is an evidence aid, not an attestation; the evidence "supports" a control.
- **Not included:** no PDF step; the HTML loads nothing external.
- First run: one tenant on the Develop connector, September 2026, checked against the saved results.

# 2026-10-27 — compliance-assessment 1.1.0

| Skill | Version | Status |
| --- | --- | --- |
| compliance-assessment | 1.1.0 | released |

**More of the tenant's own telemetry counts as evidence.**

- **Extra event sources:** CloudTrail (events, console logins and failures, IAM changes, root-account
  events, errors) and a count for any network, endpoint, cloud or identity table the tenant has. Network
  telemetry moves SC-7 and endpoint telemetry moves SI-3 from not observed to partial; the report says the
  count shows only that telemetry exists, not that rules or agents were evaluated. AU-2 lists every source
  with events. A table that matches no class is not queried.
- **Account hygiene from the existing dumps:** disabled accounts, guests, administrators, MFA registration
  of enabled users and administrators, and devices with no sign-in for 90 days. IA-2/IA-5 is partial from MFA
  registration as well as Conditional Access; the report states that registration is not enforcement.
- **Fixes:** the logging control named "September" for every month; a missing Conditional Access or Qualys
  figure now reads as not collected instead of printing "not collected" inside a sentence.
- `build_report.py --summary-json PATH` writes the control statuses and the facts behind them (including
  hygiene, devices, CloudTrail, sources and the administrator list) so other reports reuse them instead of
  repeating the queries.
- Removed the note about another connector's compliance tools.

# 2026-10-27 — incident-investigation 1.5.3

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.5.3 | released |

**Is the source address the firewall?** The generic workflow's G3 now runs
`ip_log_sender.kql` before the subnet lookup. It says whether an address sends logs itself,
and which product it is (FortiGate, VPN, router). Behind source NAT or a port forward, the
firewall's own address stands for every client: internet scanners and staff on the VPN reach
a server as the same IP. G3 now says what follows from that:

- count failures per account, not per address;
- ask who was behind the device (VPN events, traffic log, jump host), and call attribution a
  gap when nothing names a person;
- never ask the customer to identify the owner of their own firewall's address;
- never write the address into an account note as an attacker.

A run on two SSH-login incidents treated a FortiGate as "an internal host that has been
spraying the server for a month". The FortiGate's own events were in the same `default`
index the run searched. That run also wrote the address into an account note as a sprayer.
