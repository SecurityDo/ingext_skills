# 2026-10-20 — incident-investigation 1.3.0 → 1.4.0

Google Workspace incidents get their own workflow, and the skill learns a second way an
inventory lookup lies.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.4.0 | released |

## Why

**Google tickets ran the generic workflow, and it could not answer them.** On one mixed
Google + Microsoft 365 account, three `GoogleWorkspace_Login_*` tickets in two weeks went
through the generic workflow. The ticket that settled the question was a
`login_verification` / `login_success` pair, score 5000, flagged for a first-seen city
and ISP:

- The "new" address had carried the user's own OAuth token traffic for three weeks, 63
  events, and no other user had used it. The ML geo terms count **login** events only, and
  a Google session lasts days, so the first interactive login from the user's own network
  scores as a new location.
- The user's laptop synced (mobile report, same `DEVICE_ID` for 40 syncs since three weeks
  earlier) in the same second as the login, and the second factor was a passed Google
  device prompt. Neither fact is in the summary. The automated investigation reached the
  right verdict without either of them.
- One OAuth app was authorised right after the login. Its scopes (`openid`, email,
  profile) made it a sign-in-with-Google, not a data grant, but only the raw event says so.
- The account collects no `gmail` audit events, so forwarding and filters are a gap there.
  Nothing in the skill said to check which Google reports an account collects.

**A misspelled column read as an unreadable table.** The automated run filtered
`gsuiteUser` on `PrimaryEmail` (the column is `primaryEmail`). The engine returned a
result with no columns at all, the run saved "gsuiteUser has no readable fields" as an
account note, and the next runs trusted it: one escalated a ticket because it believed no
profile source existed, while the table named the subject as the company's CIO and a
Google super admin.

## What changed

- **New `references/workflows/google.md`** (W0–W6): which Google reports the account
  collects (the control for every negative); the profile from `gsuiteUser`; logins vs
  token traffic per address; the approving device and factor; OAuth grants after the
  login with their scopes; admin-console and account-security negatives; the score as
  novelty and the rule's base rate.
- **Seven bundled queries**, `assets/queries/gw_*.kql`, each validated and run on a live
  account: `gw_app_census`, `gw_address_census`, `gw_ip_users`, `gw_login_detail`,
  `gw_devices`, `gw_token_grants`, `gw_admin_on_subject`.
- **SKILL.md step 3** routes `GoogleWorkspace_` to the new workflow; generic.md no longer
  lists Google logins.
- **SKILL.md step 4**: `Columns: []` means the query named a column the table lacks.
  Read the schema and rerun before calling a table unreadable, and never record one as
  unreadable without the readability probe.

## Related portal change

The Agent Portal mounted only `incident-investigation` for an automated run, never the
sub-skills it delegates to, so `ingext-get-profile`'s correct `gsuiteUser` query was not
there to use. ingextAgent now mounts `ingext-get-profile`, `ingext-log-analytics-evidence`
and `ingext-kql` with it.

# 2026-10-20 — incident-investigation 1.4.0 → 1.4.1

Before calling an address "the organisation's own network", look it up in the tenant's own
subnet inventory. A user count only shows that an address is shared.

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.4.1 | released |

## Why

An automated run closed a Microsoft 365 MFA-registration ticket as benign. It called both
desktop addresses "the customer's own shared corporate egress". That label rested on two
things:

- `ip_census` counted 1,093 and 1,064 distinct users on the two addresses.
- An account note listed 17 "shared corporate IPs", and 43 later runs had confirmed it.

Every one of those confirmations was the same user-count census, so they added no
independent evidence. The tenant has a CIDR entity table, `Corporate_Subnets`: its IPAM
export, 1,547 ranges. Neither the skill nor the run ever looked at it. The lookup shows:

- One address is in it, in the HQ core ISP range.
- The other address, despite its 1,064 users, is not in it.
- Only 5 of the note's 17 addresses are in it.
- The table holds no IPv6 range, so it can say nothing about the subject's phone on
  cellular.

The verdict did not change. What changed is that the claim "their network" is now backed by
the customer's own inventory where it exists, and labelled "shared" where it does not.

## What changed

- **New `assets/queries/subnet_lookup.kql`:** matches the addresses against any
  `lookupType: CIDR` entity table, using `ipv4_is_in_range` or `ipv6_is_in_range`
  depending on the address family.
  - Placeholders: the table's `kqlName`, its CIDR column, a label expression, `{IPS}`.
  - Output: the matching ranges per address, and `decidable: false` when the table has no
    range of that address family.
  - Validated and run on a live account against two differently shaped CIDR tables.
- **`office365.md` 3a** runs the lookup before `ip_census`, and grades every address:
  - **owned:** an inventory match;
  - **shared:** a census count without a match;
  - **undecided by the inventory:** `decidable: false`.

  Each grade has fixed wording. 3a also says that no match is not "external", that
  "owned" settles where a sign-in came from and not who made it, and that an account note
  does not replace the lookup.
- **`okta.md` K5, `google.md` W2, `generic.md` G3** run the same lookup.
- **SKILL.md step 3:** a rule that applies to every workflow: "their network" needs their
  inventory.

# 2026-10-20 — incident-investigation 1.4.1 → 1.4.2

`datatable(ip:string)["1.2.3.4"]` as a bracket-quoted identifier ("missing '['"). The
