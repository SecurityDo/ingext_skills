Added engine caveats to `SKILL.md` and `references/kql_syntax.md`, each checked on a live tenant:

- With no `summarize` before it, `order by` sorts only within each shard and concatenates the shards unsorted, so `order by … | take N` returns the first shard's top N. `top N by` and `order by` after `summarize` sort correctly. - `coalesce()` over `tostring()` never falls through, because `tostring()` of a missing key is `""`.
- Cross-table `union` + `summarize` can over-count, and a `join` against a large stream table fails at the row cap.

## ingext-kql 1.1.3 — cross-table correlation and the search window

Root causes from the datalake team (fixes are in ingextkql/lake but not yet deployed):

- **`union` of two raw tables over-counts:** in a sharded search, a second table used as a union arm is counted once per parquet file. The skill now says to summarize each table in a `let`, union the summaries, and summarize again.
- **`join kind=fullouter` (also rightouter/rightanti/rightsemi) runs as an inner join**, which silently drops keys seen on only one side. The skill now warns against these join kinds until the fix ships.
- **`max()`/`take_any()` over strings** didn't return the populated value in a union merge. The skill now says to use `make_set_if`.
- **The search window ignores time filters inside `let` and union arms**, so it falls back to the last 24 hours. The skill now says to pass `rangeFrom`/`rangeTo` explicitly for any query with `let` or `union`.
- **`coalesce()` treating `""` as a value** is a deviation from Kusto, and a fix is pending. The `iff(isnotempty(...))` workaround stays.

Schema KB resynced from `ingext_schema`: `DuoTelephony` gains `duo-telephony-by-user`, which attributes calls/SMS to users with unioned let summaries. On gramfg it kept all 34 numbers, including those seen on only one side, and its counts match per-table queries.

## ingext-kql 1.1.4 — correct the string-aggregate note

1.1.3 blamed `max()`/`take_any()` over strings. The datalake team found the real cause: a dynamic value (`make_set` etc.) computed inside a `let` arrives at the coordinator as a string, so a `strcat_array(make_set(...))` inside the `let` was null for every row. `max()` over strings is correct. `take_any()` could still pick the null that `union` fills in for a missing column. `SKILL.md` now says to keep scalars in the `let` and aggregate or format after the union. Fixes for both are pending in ingextkql.

## ingext-kql 1.1.5 — engine fixes deployed; workarounds removed

The ingextkql/lake fixes are live fleet-wide (charts v2.10.89: account-lake 2.9.33, realtime-search 2.10.20). Each one was re-checked on gramfg before the skill changed:

- `order by` on rows with no `summarize` now sorts the merged result. The "use `top`, not `order by`" note is gone.
- Time filters inside `let` bodies and union arms set the search window, so `rangeFrom`/`rangeTo` no longer need to be passed explicitly.
- A pipeline that reads a second table directly is now refused with an error that names the union-of-lets rewrite, instead of silently over-counting. Union-of-lets remains the documented form.
- `coalesce()` skips empty strings, as in Kusto.
- `rightouter`/`fullouter`/`rightanti`/`rightsemi` joins work between lets or after a summarize; on raw table rows they are refused.
- `make_set`/`make_list` results stay arrays through a `let`, and `take_any()` prefers a non-empty value.

Still documented, because they remain open: the default join kind is `inner` (not `innerunique`), `on Key` keeps one key column (no `Key1`), an unknown column on a dynamic-schema table reads as null instead of erroring, and `summarize by X` with no aggregate does not parse (use `distinct X`).

Schema KB resynced from `ingext_schema` 6363755: the `DuoTelephony` info doc and `duo-telephony-by-user` no longer carry the workarounds. With no range passed, the union form and a fullouter join between the two lets give the same totals on gramfg (32 numbers, 312 messages, 552 credits, 273 phone auths over 7 days).

# 2026-10-30 — windows-server-activity-report 1.0.0 (new), fortigate-security-activity-report 1.0.0 (new)

| Skill | Version | Status |
| --- | --- | --- |
| windows-server-activity-report | 1.0.0 | released |
| fortigate-security-activity-report | 1.0.0 | released |

**Two more archive-only activity reports**, built the same way as `microsoft365-entra-activity-report`
and `aws-cloudtrail-activity-report`: they list the archive of a scheduled report, download the daily
results, merge them (counts add, distinct counts are the peak day, top-N lists are lower bounds, a gap
is never a zero) and render HTML, PDF and CSV. They never run a live search.

- **windows-server-activity-report** reads the archive of `WindowsSrv_Activity_Report`, four scans over
  `WindowsAudit`. It covers everything `WindowsSrv_Ingress_Search_Report` returns (events, hosts, events
  and bytes by host and by event ID, with `AD_EventID` names) and adds user logons and failures,
  failed-logon sources, privileged logons, account and group changes, services and tasks installed, and
  audit-log clears and policy changes. On navasotavalley (29 Oct 2026) `WindowsAudit` matched the older
  nxlogAD events event ID for event ID (838,723 against 838,771; the 48 extra have no event ID). The
  processor is `fplProcessors/code/WindowsSrv_Activity_Report.js` in the Scripts repo (id 720181).
- **fortigate-security-activity-report** reads the archive of `Fortigate_Security_Activity_Report`: failed
  SSL-VPN logins by device, country, source and user, sessions and tunnels, application-control and
  web-filter blocks, IPS and DoS anomalies, and administrator logins and configuration changes.

Both name users and source IP addresses, so the report is personal data; `--no-actors` builds a copy
without those lists.
