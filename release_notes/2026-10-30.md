## ingext-kql 1.1.2 — Duo resync and engine sorting caveat

Synced the schema KB from `ingext_schema` 6a58bbd (50 tables; `--check` passes). Only the Duo tables changed:

- **`DuoTelephony` (new):** one record per call/SMS Duo placed, with `type`, `context`, `phone` (E.164) and `credits`. It carries no user, application or IP, so a number is attributed by pivoting to `DuoAuthentication.auth_device.name`, which uses the dashed national form. Three example queries: daily credit use, numbers contacted repeatedly in an hour, and admin-panel SMS logins with enrollment SMS.
- **`DuoAdmin`:** `descriptionFields` keys arrive with spaces and dots stripped (`Usersadded`, `SyncRefCode`); the old `["Users added"]` spelling returned null, so `duo-directory-sync-health` never returned data. Rewrote it as a per-day summary that also counts `ad_sync_failed`. Documented `ad_sync_failed`, `user_pending_delete`, `user_restore`, `user_remember_me_revoked`, the `System` actor, the `admin_login` detail keys and status `Bypass`. New query `duo-admin-bypass-status`.
- **`DuoAuthentication`:** documented the factor and reason values seen in live data, a null `factor` on `bypass_user` logins, and a populated `adaptive_trust_assessments` (`remember_me`, `more_secure_auth`).

Added engine caveats to `SKILL.md` and `references/kql_syntax.md`, each checked on a live tenant:

- With no `summarize` before it, `order by` sorts only within each shard and concatenates the shards unsorted, so `order by … | take N` returns the first shard's top N. `top N by` and `order by` after `summarize` sort correctly. Root cause found by the datalake team; the fix in ingextkql is pending deployment.
- `coalesce()` over `tostring()` never falls through, because `tostring()` of a missing key is `""`.
- Cross-table `union` + `summarize` can over-count, and a `join` against a large stream table fails at the row cap.

Rebuilt `cowork/ingext-kql.skill` with `build_catalog.package_skill`; its contents match the source folder file-for-file.

## ingext-kql 1.1.3 — cross-table correlation and the search window

Root causes from the datalake team (fixes are in ingextkql/lake but not yet deployed):

- **`union` of two raw tables over-counts:** in a sharded search, a second table used as a union arm is counted once per parquet file. The skill now says to summarize each table in a `let`, union the summaries, and summarize again.
- **`join kind=fullouter` (also rightouter/rightanti/rightsemi) runs as an inner join**, which silently drops keys seen on only one side. The skill now warns against these join kinds until the fix ships.
- **`max()`/`take_any()` over strings** didn't return the populated value in a union merge. The skill now says to use `make_set_if`.
- **The search window ignores time filters inside `let` and union arms**, so it falls back to the last 24 hours. The skill now says to pass `rangeFrom`/`rangeTo` explicitly for any query with `let` or `union`.
- **`coalesce()` treating `""` as a value** is a deviation from Kusto, and a fix is pending. The `iff(isnotempty(...))` workaround stays.

Schema KB resynced from `ingext_schema`: `DuoTelephony` gains `duo-telephony-by-user`, which attributes calls/SMS to users with unioned let summaries. On gramfg it kept all 34 numbers, including those seen on only one side, and its counts match per-table queries.

## ingext-kql 1.1.4 — correct the string-aggregate note

1.1.3 blamed `max()`/`take_any()` over strings. The datalake team found the real cause: a dynamic value (`make_set` etc.) computed inside a `let` arrives at the coordinator as a string, so a `strcat_array(make_set(...))` inside the `let` was null for every row. `max()` over strings is correct. `take_any()` could still pick the null that `union` fills in for a missing column. `SKILL.md` now says to keep scalars in the `let` and aggregate or format after the union. Fixes for both are pending in ingextkql.
