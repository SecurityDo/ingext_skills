# 2026-09-19 — new skills: setup-aws-guardduty-connector, incident-investigation

Two new skills.

**setup-aws-guardduty-connector.** Sets up the **Amazon GuardDuty** connector end to
end using an STS assume-role instead of an access key, now that the `AmazonGuardDuty` app template
carries an `AWS_Role` parameter. For what the skill does and its trigger phrases, see its section in
the root `README.md`.

**incident-investigation.** Works an escalated Fluency behavior incident to a
verdict. It came out of triaging a passkey-registration incident on a customer tenant
that the AI-assist workflow had already marked actionable and escalated at medium likelihood
of compromise. It was benign, and the skill encodes the checks that showed it.

# setup-aws-guardduty-connector

## Implementation notes

- **Modelled on `setup-aws-cloudtrail-connector`** — same division of labour (the customer runs the
  CloudFormation, Claude drives the Fluency-side tools), same shared trust-only role
  (`IngextSaasPodRole.yaml` → `ingextAssumeRole`, created once per account and reused across
  integrations), same `add_assumed_role` → `test_assumed_role` → `create_connector` tail. Each tool
  is listed with its `ingext` CLI equivalent, since internal installs go through the CLI.

- **It is an API poll, not an S3 delivery.** The connector's data source is a platform *plugin*
  (`Integration type: AWSGuardDuty`) that calls `ListDetectors` → `GetDetector` → `ListFindings` →
  `GetFindings` per region. No bucket, no SQS queue, no prefix. The skill says so early, because
  everything else in the AWS connector family is S3-shaped. If someone hands over a bucket name they
  mean GuardDuty's S3 *export*, which is the CloudTrail skill's flow with a different connector.

- **`GuardDutyRole.yaml`'s `IAMRole` default is a trap.** It ships as
  `fluencyplatform_instancerole`, the legacy on-prem EC2 instance role, and attaches the managed
  policy to an *existing* role. Left at the default the stack either fails (no such role) or succeeds
  against an unrelated role, after which the connector cannot read anything. The skill overrides it
  to the step-2 role in the parameter table, the CLI example, and the failure-mode table. The policy
  is region-independent (`Resource: "*"`), so one deployment covers every polled region.

- **The step with no analogue in the S3 skills: confirm a detector exists.** The connector reads
  findings and cannot enable GuardDuty. A region with GuardDuty off returns no findings, the poll
  succeeds, and nothing reports a problem — a silent empty index. The skill makes
  `aws guardduty list-detectors` a required per-region check before install, and carries the three
  things that make enabling a decision rather than a detail: it bills on volume analysed (flow-log GB
  being the usual surprise, and GuardDuty ingests flow logs from the VPC whether or not the account
  stores them); a new detector enables `EBS_MALWARE_PROTECTION` **by default**, which is expensive
  where node churn is heavy; and the 30-day free trial cannot be checked before enabling, because
  `get-remaining-free-trial-days` needs a detector id — the trial is per account per region, so an
  account that previously enabled and removed GuardDuty bills from the first minute.

- **Findings land as RESOURCES, not datalake events** — established by running the install for real
  on an internal audit tenant. The app creates a `GuardDuty` datalake index and declares a DataSink,
  but the plugin writes each poll to the resource store as `GuarddutyFinding`: one sample finding
  produced one resource hit and **zero index rows**. The skill's first draft told the reader to verify
  with a KQL query on the index, which would have reported a working connector as broken. Verification
  is now `ingext resource --resource-type GuarddutyFinding`, with the `platform-0` log lines that
  narrate a healthy poll (`Downloading …plugin_awsguardduty`, `Wrote N rows … .parquet`, `Added
  resource dump info`).

- **The hosting account cannot use the assume-role flow.** saasmgr rejects registering any role whose
  ARN is in the hosting account (`cannot manage roles in the hosting account`, deliberate
  self-protection in `account_api_handler.go`), and there is no ambient-credential fallback —
  `getAuthInfo` requires one of accessKey, user or role. The route for that case is the **local** role
  registration (`platform_instancerole_add_local`, `ingext eks add-local-assumed-role`), which records
  a role that already exists instead of asking saasmgr to manage one. Proven end to end on the
  an internal audit tenant against a hand-created role. The skill carries both the constraint and the
  local-registration escape.

- **Verification does not wait for findings.** A healthy GuardDuty in a quiet account produces none
  for days, so an empty index proves nothing. The skill uses
  `aws guardduty create-sample-findings` — real API objects that traverse role, permissions, poll and
  sink — then queries the index. It also notes the install creates its own `GuardDuty` datalake index
  against the built-in `GuardDuty` schema, so no index has to be made by hand.

- **Multi-region encoding is flagged as uncertain, not guessed.** `Regions` is a list, but
  `ingext application install --config` takes `key=value` pairs separated by commas, so a
  comma-separated list may not parse as one value. The skill recommends `create_connector` (JSON
  array) or one instance per region for multi-region, and notes the latter makes regions
  independently removable.

# incident-investigation

## Implementation notes

- **The base rate closes more tickets than everything after it.** The skill's step 2 asks one
  question before any per-user analysis: how many other entities fired the same rule this
  week? On the worked incident the answer was 33 distinct users in seven days, **12 of them
  raised as incidents with a byte-identical risk signature** (`ALERT_SEVERITY_HIGH` +
  `ML_NEW_USER`, riskScore 3600), against 55+ accounts registering passkeys over five days.
  The ticket was the twelfth copy of one IT rollout. Nothing downstream could have overturned
  that, and everything downstream was cheaper to read once it was known. `summary_digest.py
  --rule <name>` is that query, and it warns when more than five entities are involved.

- **Resolve the IP against the tenant, not against the user.** The strongest-looking indicator
  was a Cloudflare IPv6 the user had never used, geolocated 800 miles from their office. One
  query over the whole tenant found two unrelated employees on the same `2a09:bac2::/32`,
  both on Apple devices through *Apple Internet Accounts* — iCloud Private Relay, which
  egresses via Cloudflare. The companion query settles the opposite case just as fast: the
  "new" corporate address the user had moved to on 09-14 carried 29 users and 1232 sign-ins.
  `ip_census.kql`, `ip_users.kql` and `ip_prefix_sweep.kql`.

- **The fact that decides an MFA case is in neither the summary nor the sign-in log.**
  `StrongAuthenticationPhoneAppDetail` in the `Office365` `ModifiedProperties` names the
  device that satisfied MFA, and diffing its `OldValue` against `NewValue` says whether that
  device was already enrolled. Here an `iPad Pro (12.9-inch) (5th generation)` had been an
  enrolled factor since 09-04, authenticated 52 seconds before the registration, and its
  user-agent matched the registration session — an attacker would have needed the user's own
  iPad. `auth_method_changes.kql`.

- **A benign verdict is a set of negatives, and they have to be collected.** `bec_sweep.kql`
  covers thirty days of what an actor does *after* taking an account — inbox rules,
  forwarding, delegated mailbox access, transport rules, OAuth consent — in one query; zero
  hits is the evidence. `user_registration.kql` asks the other half: not what was added but
  what was **removed or demoted**. The account finished with five auth methods and its
  preferred secondary method unchanged, which is a rollout's signature, not persistence.

- **Four traps that manufacture findings, all of which fired on this ticket.** Error codes are
  not interchangeable — the reported "6 failed logins followed by a successful sign-in" was
  five `50126` on the user's own Entra-joined compliant laptop at the corporate egress, each
  followed by success seven seconds later, mixed with `50074` MFA interrupts and `70044`
  session expiries. Azure's `DeviceDetail.operatingSystem` disagrees with the real
  `UserAgent` (`Ios 26.6.2` against `iPhone OS 18_7`), so the OS label invents new devices.
  Rows are duplicated — 224 sign-in rows deduped to 175, so any hand count is inflated.
  And "UPN/email domain mismatch" was the house convention for 808 of the tenant's users.
  The skill carries the error-code table, and `kql_rows.py` dedupes and says how many it
  dropped.

- **`eventwatch search_summary` throws its own response away.** The CLI prints a
  `Key: …, RiskScore: …` line per hit and nothing else; the document exists only inside the
  `-l debug` log, pretty-printed in a Go slog `msg="…"` field. `ingext_json.py` runs the
  command and recovers it, and prints the resolved `siteURL` to stderr — because `--cluster`
  and `-n` are accepted and ignored, and the only thing that switches tenant is
  `ingext config use`. `--query` is free text, not a key filter: one search for one username
  returned 69 summaries across 40 accounts on a single-domain tenant.

- **`incidentDetectionTime` is not event time.** The AI-assist summary quoted
  `03:14:26.139Z`; the directory audit puts the activity at 03:06:16–03:06:48. A timeline
  built from the ticket starts eight minutes late.

- **Closing the ticket is not finishing the job.** When the base-rate check finds a campaign,
  the skill requires the tuning condition to be written out concretely before closure — here,
  suppress when the change is self-initiated *and* MFA was satisfied on an already-registered
  device *and* no method was deleted. Otherwise the same verdict gets written eleven more
  times. `eventwatch-rule` is the skill that then writes it.

- All twelve queries parse-validate against a live tenant (`ingext kql validate`), and the
  three scripts were run against the real incident's saved responses.
