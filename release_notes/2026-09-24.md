## ingext-get-profile 1.0.0 — what an entity IS, on one account

### Why

incident-investigation 1.2.0 established the subject's privilege with
`get_azure_user_record` only, which assumes every subject is a Microsoft 365 user. On a
Google Workspace tenant that call returns "not found" — and it did, on a live run, for a
user who also had Microsoft 365 sign-ins in the event stream but no `office365User`
table on the account. The procedure had no way to say "this is a Google user, here is
the profile" and no way to say "the Microsoft directory record is unavailable here"
without it reading as "no roles".

### What it does

- **Determines the entity type from the account's resource tables.** One
  `list_data_tables` call; `gsuiteUser` → Google Workspace user, `office365User` →
  Microsoft 365 user, `gsuiteGroup` / `office365Group` → groups. Every present table is
  queried (an entity can be in both directories), never just the first.
- **Bundled, parse-validated queries** in `assets/queries/`: users by primary address,
  **any alias** (Google `emails[]` / `nonEditableAliases[]`), UPN, `mail` (finds guests)
  or object id; groups by object id first, display-name matches returned in full rather
  than picked.
- **Validates before it runs.** `validate_kql` on every substituted query, then
  `kql_search`.
- **Microsoft users also get the live record** via `get_azure_user_record`, which wins
  over the snapshot when they disagree.
- **Returns a normalized profile** — `status`, `privilege` (admin flags + full role
  list), `mfa`, `aliases`, `recovery`, `groupType`, plus `tablesChecked` and `gaps` so a
  caller can tell "not found" from "could not check".
- **Inherits the caller's single-account boundary**; "not found on this account" is an
  answer, never a reason to search other accounts.

### Traps carried in the skill

- "Not found" from `get_azure_user_record` without an `Office365ResourceWatch`
  integration is a gap, not proof of no roles.
- Google admin flags are absent when false — the queries coalesce them; a matched row
  whose every column is null is reported as a gap, never as "not an admin".
- Privilege is never inferred from the absence of role-assignment audit events (moved
  from incident-investigation 1.2.0).
- Group display names are not unique; resolve by object id (moved from 1.2.0).

### Empty result ≠ not found

- **Readability probe** (`assets/queries/readability_probe.kql`, step 2.4). When a match
  query returns zero rows, one aggregate counts the table's rows and how many carry a
  non-empty key column. Rows with no readable keys, or no rows at all, become a named gap;
  only a readable table can contribute to `found: false`, and a kind whose every table
  failed the probe is reported as unknown.
- Found on a live run: a Google Workspace group table with 98 rows and every field except
  `_key` null. The group lookup returned zero rows, which would have read as "this address
  is not a group". The probe reports 98 rows / 0 readable.

### Devices

- **Five device tables** mapped the same way: `msDefenderMachine`, `office365Device`,
  `sentinelOneAgent`, `falconAgent`, `qualysHost`, each with a bundled query matching the
  short host name, the FQDN and the vendor's own ids; plus one `asset_search` cross-check
  against the platform inventory.
- **Behavior-summary ids are normalized** (step 0): `asset_<host>_<YYYYMMDD>` →
  entity `<host>`, kind `device`; `username_<upn>_<date>` → user.
- **One match per source table plus a merged `device` summary** — OS, hardware, last
  user (OS account and AD name), internal/external IPs, join and compliance state, AD
  OU, EDR coverage with each agent's own health and last-seen time, Defender risk and
  exposure, and the id used to join records (`aadDeviceId` = `office365Device.deviceId`).
- **Traps:** agents that disagree about "online" are both reported, not merged; Defender
  risk and exposure are separate axes; a host known to Entra with no EDR row is a coverage
  gap; `office365Device.username` can be the string `None`; the asset inventory can hold
  only log-derived hosts.

## incident-investigation 1.2.1 — depend on ingext-get-profile

- New **"Depends on"** section naming `ingext-get-profile` (step 1), with a fetch-the-package
  fallback when it is not installed.
- Step 1's "Who is the subject?" section now invokes the sub-skill for the subject **and
  every target account or group**, and says what to carry forward: `privilege` for
  the step-3 workflow, `found: false` / `gaps` as findings in the closure, `recovery` and `aliases` for
  the step-3 workflow.
- The inline `get_azure_user_record` call and the `office365Group` query were removed from
  this skill; they live in the sub-skill.
- MCP tool table, "Tables used" and "Related skills" updated.
- **Step 1 split into two entry cases:**
  - *Case 1 — a ticket id* (`<keyType>_<key>_<YYYYMMDD>`): fetch it directly with
    `searchStr: id:"<id>"`, always quoted (an id carrying an email is split on `@`/`.`
    when bare). Expect `total: 1`; a zero means a wrong id or a window that misses the
    id's date.
  - *Case 2 — an entity only*: `mustFilters` on `key` with the key **lower-cased**
    (`key` is stored lower-case; an upper-case host name returns 0), `limit: 1`, and
    facets on `id`, `dayIndex`, `behaviorRules`, `status`, `classification` with
    `facetSize: 50`, filtered to `incident: true` and sorted on `to` descending, so the
    one returned document is the **latest ticket**. The default `riskScore` sort would
    return the highest-scoring one instead; without the incident filter "latest" is the
    latest activity day (on the test entity, a zero-score sign-in day). Facet buckets
    sort by count, not time, so "latest" is never read off a facet.
  - The old guidance — a quoted `searchStr` for an entity — is gone: it matched whole
    documents, not keys.
  - Measured while writing it: `facetSize` defaults to 20 and dropped 5 of a user's 25
    daily ids over 30 days; `limit: 0` is not honoured and returned 20 full documents
    (~150 KB).
- **Steps 3–5 replaced by a workflow chosen by incident type.** The procedure is now:
  0 tenant → 1 ticket + profile → 2 base rate → **3 run the workflow for the type** →
  4 re-derive every number (was 6) → 5 verdict (was 7) → 6 closure report (was 8).
  - Step 3 routes on the ticket's `behaviorRules` prefix (`O365_` / `AzureAD_` /
    `Fluency_O365_` → Office365), falling back to the rule's `group` from
    `eventwatch_rule_list`. A ticket with several types runs each workflow.
  - `references/workflows/office365.md` holds the old steps 3–5 as 3a (resolve every
    address), 3b (approving device — now explicitly auth incidents only, otherwise "not
    applicable") and 3c (prove what did not happen), plus the tables it reads. 3a now
    resolves every address on the ticket, and more when needed (the raw action's IP,
    the subject's other sign-in IPs, addresses 3c turns up), naming the extras.
  - Every other type (SentinelOne, Google Workspace, …) runs
    `references/workflows/generic.md` rather than a dedicated workflow: G1 read the raw
    events by stable id, G2 how common the fired-on artifact is in the inventories, G3
    resolve every indicator against the tenant, G4 timeline from raw time (including when
    the artifact started and when the rule appeared), G5 negatives chosen by entity kind,
    each with a control, G6 side findings kept separate. Its checks are labelled
    "generic workflow — improvised" in the closure; a type that goes through it twice is
    the cue to write a dedicated workflow. Distilled from the SentinelOne ScreenConnect
    run; no queries are bundled with it.
  - Cross-references, the closure section order and `assets/closure_schema.md` renumbered.
- **Step 2 base rate runs once per rule** on the ticket, as a tested
  `behavior_summary_search` call (rule filter, 7 days, facets on `key`, `dayIndex`,
  `status`, `classification`). A combined multi-rule filter matches any rule and blurred
  an app-registration ticket's base rate from 1 to 2. Background rules that fire for
  everyone daily are skipped. The CLI form moved into a collapsed block.
- **Bundled queries are run as written** — no summarising, dropped columns or filtered
  rows to shorten output; an oversized result is read from its saved file instead.
- **Office365 workflow 3c profiles the application** when the subject acted on one:
  new `app_registration.kql` (`office365Application`) and `app_service_principal.kql`
  (`office365InstalledApp`), keyed on the audit event's `appId`, read against the audit
  trail. A just-created app missing from the snapshot is a timing gap. The subject stays
  the user; apps are not added to `ingext-get-profile`.
- **Empty result ≠ not found, carried through the investigation:**
  - Step 1 reads the profile's `gaps` before `found`: a kind whose table failed the
    readability probe is unknown, never "not a group" / "not an admin", and each gap goes
    into the closure as "not verified — <reason>".
  - The Office365 workflow's `user_registration.kql` (3c, a snapshot lookup) gets the same rule: a zero-row
    result is checked with the probe, or the step-1 profile is reused.
  - Step 4 (re-derive) gains the trap "an empty snapshot lookup is not an empty directory", with the
    probe as its control. The "Seven traps" heading, already out of date, now reads "The
    traps".
  - Step 6's (closure report) "no zero without a control" rule maps every profile gap to a written gap and
    makes the probe the control for a directory lookup's zero.

- **Subject history is a required step.** A case-1 ticket fetch returns one document and
  nothing looked backward at the subject, so earlier related tickets were missed. Step 1
  now lists the subject's other tickets from the last 30 days (current ticket excluded)
  and re-reads any whose rules are a precursor or sibling of today's.
- **Base-rate calls exclude the ticket itself** (`mustNotFilters` on `id`). With `limit: 1`
  each per-rule call previously re-sent the full ticket.
- **App credential use is checked.** When a secret or certificate is added to an app, the
  Office365 workflow runs `app_signins.kql`, `app_actions_audit.kql` and
  `app_actions_o365.kql` (new `{SPID}` placeholder), each against a control. It also records
  that `AzureSigninLogs` holds user sign-ins only, so the secret's own token use is a gap,
  not "unused".

- **SentinelOne workflow.** New `references/workflows/sentinelone.md`, routed from the
  `SentinelOne:` prefix in step 3 (previously handled by the generic workflow). Seven parts:
  pull each alert whole with `investigate_sentinelone_alert`; decide running vs at rest from
  `initiatedBy` and the engine; place the agent by `registeredAt` and last user (the live
  record wins over the lagging `sentinelOneAgent` snapshot); hash prevalence, origin, prior
  executions and earlier analyst verdicts via `lake_search`; negatives with controls and the
  pre-install gap; threat/alert/summary reconciliation; score inflation from file-named
  vendor rules and vendor-side tuning. Written from three SentinelOne tickets.

## Verification

- Device profiling run end to end on a hybrid-joined Windows 11 laptop on an MSSP tenant,
  starting from its `asset_<host>_<date>` summary id: Defender, Entra/Intune and
  SentinelOne all matched (short name vs FQDN vs upper-case display name), the Defender and
  Entra records joined on `aadDeviceId`, and `asset_search` returned no endpoint (that
  account's inventory holds firewalls only) — recorded as a note.
- Readability probe run live on three tables: the unreadable Google group table (98 rows /
  0 readable), a readable Google user table (143 / 143) and a readable Defender table
  (4311 / 4311).
- `falcon_agent.kql` and `qualys_host.kql` parse-validated only. The first Qualys draft sent
  the validator to a 500 on an untyped bracketed column; every such column is now wrapped
  in `tostring()`.

- `gsuite_user.kql` run live on a Google Workspace tenant: the primary address and an alias
  both resolved to the same single user; coalesced flags returned `false`, not `null`.
- `office365_user.kql` and `office365_group.kql` parse-validated with `validate_kql`; not run
  against live `office365User` / `office365Group` data in this release.
- `gsuite_group.kql` parse-validated. On the test tenant every column except `_key` came
  back null — recorded in the skill as a known gap and the reason for the all-null trap.
- `cowork/ingext-get-profile.skill` built; `cowork/incident-investigation.skill` rebuilt
  with no file added or removed. `scripts/validate_skills.py --worktree` passes; the new
  skill's description is 939 characters.
- Both skill folders and packages scanned for tenant names, customer domains and people:
  examples use `contoso` placeholders.
- New app-activity queries run live on an app-registration ticket: all three returned zero
  for the new app, and each matched a known-active principal as a control. The Office365
  query's first draft used `has "<guid>"` on `UserId` and returned 0 for the control; exact
  equality returned 119, so the bundled query uses equality.
- SentinelOne workflow drafted from three live tickets (one remote-access tool, two
  first-scan payload detections); its search templates are the calls those runs made. Not
  yet run end to end as a workflow.
