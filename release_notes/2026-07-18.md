# 2026-07-18 — new skill: o365-activity-report (account-wide O365 activity, KQL)

One new skill. `o365-activity-report` produces an **account-wide** (whole-tenant, not a
single user) Microsoft 365 activity report by querying the `Office365` datalake table
directly with **KQL** and rendering the results as a KPI strip, a **timechart**, and
ranked breakdown **tables** in a self-contained HTML page (optional PDF).

It closes a gap between the two existing O365 report paths: `office-user-investigation`
is KQL but scoped to **one named mailbox**, and `fluency-report` runs a **saved FPL
report** from the catalog. Neither covers "give me an Exchange/O365 activity report for
the whole account over the last N hours, from KQL, with a table and a timechart" — which
is exactly what analysts reach for when they spot a workload/operation spike (e.g. an
`Office365` event hike dominated by `MailItemsAccessed`). This skill is that path.

## Implementation notes

- **Three focuses.** `focus=exchange` (Exchange mailbox activity — operations, top users,
  top source IPs), `focus=mailitemsaccessed` (a drill-down into the MailItemsAccessed
  operation — most-accessed mailboxes, source IPs, external-vs-owner logon split), and
  `focus=all` (every workload, timechart split by `Workload`). The agent infers the focus
  from the request and runs the matching KQL set via `kql_search`, passing the window as
  `rangeFrom`/`rangeTo` ms (no inline time filter), saving each raw result to
  `<workdir>/<name>.json`.

- **Deterministic, fabrication-proof rendering.** `scripts/build_report.py` reads the
  saved KQL JSON (tolerant of the raw `data.Tables[0]` tool envelope) and renders every
  KPI, chart point and table row **directly from the data**. A query that is missing or
  returns zero rows renders an explicit **"no data in this window"** panel rather than a
  filled-in guess, and a **"Data sources"** appendix lists each query file with its row
  count so every figure is traceable. This is a direct response to the "report looks fine
  but the numbers are fabricated" failure mode — the renderer is a script precisely so the
  model cannot hand-write figures into the HTML.

- **Self-contained output.** Inline CSS + inline SVG line chart (no external fonts,
  scripts, or CDNs) so it renders in the Cowork/artifact sandbox. PDF is optional via
  WeasyPrint; if its libs are absent, build HTML only and convert with `html-to-pdf`.

- **Field basis.** Uses the verified `Office365` unified-schema fields: `timestamp`,
  `Operation`, `Workload`, `UserId`, `ResultStatus`, `ClientIPAddress`, `MailboxOwnerUPN`,
  `ExternalAccess`, `LogonType`. Timechart bin is chosen from the window (≤2d → 1h).

## Guardrails / routing

- Wrong-skill guards documented both ways: a request scoped to **one mailbox** routes to
  `office-user-investigation`; a request to run a **saved/FPL report** routes to
  `fluency-report`. The description makes the "account-wide, KQL, not FPL" trigger explicit.

## Update — fail loud on unsaved query results (v1.0.0 hardening)

First live run surfaced a failure the initial design allowed to pass quietly: the tables
came back **blank while the data-derived summary looked right**. Root cause is the
save step, not the queries — the summary reads `overview.json` + `timechart.json` (and
what the model already saw in context), whereas every table panel reads a **separate**
`<name>.json`. The model had run the queries but not persisted each result to its file
(commonly the "Output too large → saved to a path" case), so the renderer saw no rows and
drew "no data" per table. The report *looked* finished, which is the trap.

The renderer now distinguishes a file that **returned zero rows** (truthful `empty`,
build stays green) from one that was **never written** (`MISSING`, a build defect):

- Any MISSING required result stamps a red **INCOMPLETE REPORT** banner at the top of the
  HTML, marks the panel MISSING (not "no data"), prints an `INCOMPLETE: …` list to stderr,
  and makes `build_report.py` **exit non-zero (3)** — so a half-empty report cannot be
  delivered as if it were a quiet window.
- `SKILL.md` gains a **save-as-you-go** rule (write each result to its file immediately
  after its query, never batch), a **Step 3.5 verify** (`ls -la` the workdir before
  building), and a Step 4 gate: a non-zero exit means re-run + save the MISSING files,
  then rebuild — never deliver an INCOMPLETE report. The failure-modes table names the
  "tables blank but summary looks right" symptom explicitly.

No schema, query, or field changes — same v1.0.0, hardened orchestration + renderer.
