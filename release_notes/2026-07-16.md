# 2026-07-16 — new skill: create-ingext-audit-app-azcli (az CLI + run-it-directly)

One new skill. `create-ingext-audit-app-azcli` is the **Azure CLI (`az` / Bash)** counterpart of
`create-ingext-audit-app`. Same `ingext-audit` registration, same nine **Application** permissions
across Microsoft Graph and the Office 365 Management APIs, same three-field output
(`tenantId`, `clientId`, `clientSecret`) for the downstream install-application stage. What's new is
the tooling (az instead of PowerShell + Microsoft.Graph) and a **run-it-directly** capability.

The existing `create-ingext-audit-app` is written around one assumption: *Claude cannot run this*,
because it targets a **third-party customer's** tenant that Claude has no credentials for — so its
job is to guide an admin. That assumption doesn't hold when the **cowork operator is themselves the
Global Admin** of the target tenant and cowork is running on their own machine. There, an
interactive `az login` happens locally, and cowork can drive the setup under the normal per-command
permission approval. This skill makes that case first-class without losing the guide-only path.

## Implementation notes

- **New skill `create-ingext-audit-app-azcli` (1.0.0).** Standard `SKILL.md` + `assets/` + `evals/`
  layout, cloned from `create-ingext-audit-app` so the permission set, the "job ends at three
  fields" contract, and the security posture are identical. Only the tooling and the mode branching
  differ.

  - **Mode A / Mode B branching is the point.** `SKILL.md` opens by asking who is at the keyboard.
    **Mode A** — the operator *is* the target tenant's Global Admin: cowork confirms the tenant via
    `az account show`, runs the bundled `setup-ingext-audit.sh` here, and captures the JSON output.
    **Mode B** — a different tenant / another admin: cowork does **not** authenticate there (it
    can't) and instead hands over the script (Path B1) or the portal walkthrough (Path B2). The
    distinction is stated explicitly so the run-it-directly capability never leaks into a tenant
    cowork has no business creating apps in.

  - **`assets/setup-ingext-audit.sh` — the az CLI translation.** Behaviourally matched to
    `setup-ingext-audit.ps1`: idempotent (reuses an existing `ingext-audit`, appends a fresh
    secret), resolves every permission's app-role ID at runtime from the resource service principal
    (`az ad sp show --query "appRoles[?value=='…' && contains(allowedMemberTypes,'Application')]"`),
    so **no per-permission GUIDs are hardcoded** — only the two resource appIds. Consent is one
    `az ad app permission admin-consent` call with a retry loop for directory-replication lag, in
    place of the PowerShell per-assignment loop.

  - **Guard rails on the run-it-directly path.** The script does a preflight (`az` present +
    logged in), prints the target **tenantId + signed-in account** before touching anything, and
    **stops for an interactive confirmation** ("Create/update app … in the tenant above?") unless
    invoked with `--yes`. `SKILL.md` tells cowork to surface that prompt and to pass `--yes` only on
    explicit operator approval — a wrong-tenant guard, since the whole risk of Mode A is creating
    the app somewhere it shouldn't exist.

  - **stdout is the contract.** All progress goes to **stderr**; the **only** thing on **stdout** is
    the `{ tenantId, clientId, clientSecret }` JSON object, so a calling onboarding task can parse it
    deterministically. The client secret is emitted once and flagged as a credential not to echo
    into logs or long-lived chat beyond the hand-off.

  - **Login guidance for headless machines.** `az login --use-device-code` is documented as the
    fallback when there's no browser on the machine cowork runs on — the operator completes the
    device-code step in a browser while cowork drives the rest.

  - **Secret expiry expressed in years.** The PowerShell skill takes `-SecretMonths 24`; the az
    variant takes `--secret-years 2` (same 24 months) because `az ad app credential reset` uses
    `--years` and avoids a non-portable `date` computation across Linux/macOS.

  - **Evals (3).** Mode A ("I'm the Global Admin — run it for me"), Mode B (Linux customer,
    az-preferred, guide path), and an explicit "az CLI, not PowerShell" tooling selection. The evals
    encode both the mode selection and the shared three-field contract.

- **`cowork/create-ingext-audit-app-azcli.skill`** built from source with `zip` (worked here; the
  05-15 mount issue that forced Python's `zipfile` for `customer-onboarding` did not recur). Archive
  root `create-ingext-audit-app-azcli/` containing `SKILL.md`, `assets/`, and `evals/` — the
  skill-name-root convention the twelve non-flat archives use. Verified: extracted tree is
  byte-identical to source (`diff -r` clean) and the `.sh` retains its executable bit (`-rwxr-xr-x`),
  which Mode A needs to run it.

- **README.** Added a "Skills at a glance" row and a detail section positioned as the sibling of
  `create-ingext-audit-app`, with the Mode A / Mode B split spelled out.

## Note — trigger overlap with `create-ingext-audit-app`

This skill and `create-ingext-audit-app` intentionally cover the same registration, so their trigger
phrasing overlaps. The descriptions differentiate on tooling ("az CLI / Linux / macOS") and intent
("run it for me / I'm the Global Admin"). Skill selection between the two is worth spot-checking with
a few prompts — a prompt that mentions neither PowerShell nor az, and doesn't say who is running it,
is genuinely ambiguous and either skill is a reasonable pick.
