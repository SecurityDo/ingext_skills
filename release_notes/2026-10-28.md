# 2026-10-28 — incident-investigation 1.5.4

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.5.4 | released |

**DLP matches: read the message before describing it.** The Office365 workflow has a new
check, 3e, and a bundled query, `dlp_message.kql`. For each `DlpRuleMatch` the query
returns From, To, CC and BCC, the subject, the policy and rule, `RuleMode`, severity,
actions, `AccessScope`, and which sensitive types matched in which attachment. 3e says:

- direction comes from `From`, never from "FW:" or "RE:" in the subject;
- `AccessScope: IncludeExternalUsers` means an outside recipient; name its domain, and
  don't call mail "internal" without reading every recipient;
- a test-mode rule (`TestWithoutNotifyUser`) blocked nothing; say so;
- check whether the recipient asked for what was sent before calling it business;
- the takeover checks still run, and a shared mailbox's sender is in `send_audit_ctl.kql`.

Two blind runs on one SSN DLP ticket described the same outbound message as "inbound mail"
and as "internal mail forwarded to the mailbox". One of them listed "recipients not
enumerated" as a gap and still called the mail internal. The message was the shared
mailbox sending an employer statement to the outside carrier that had asked for it.
The verdict, benign, was right; the account of what left was not.

# 2026-10-28 — incident-investigation 1.5.5

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.5.5 | released |

**File movement: who moved it, where, and who it was shared with.** The Office365
workflow has a new check, 3f, and a bundled query, `file_movement.kql`, for upload,
download, sync and sharing tickets. The query lists every upload, download, sync, copy,
move, sharing and link operation for the subject. For each one it gives the acting app,
the AI agent (`AgentName`), whether it was in the subject's own OneDrive or another site,
the link scope and the recipients the audit names. 3f says:

- the app and agent come before the user: Copilot writes and shares as the user;
- read the sharing rows, never only the uploads; an Anonymous or Organization link or an
  external recipient escalates; SpecificPeople link recipients the audit doesn't name are
  a gap;
- writes outside the user's own OneDrive, or agent work outside any sign-in by the user,
  are the cases to escalate.

A blind run on a `FileUploaded_Multiple` ticket searched uploads, downloads, edits and
deletes only. It never saw the 67 SpecificPeople sharing links Copilot created in the same
hours, or the Copilot agent reading 23 documents from 15 sites. The verdict, benign, was
right; the account of what moved was not.

# 2026-10-28 — incident-investigation 1.5.6

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.5.6 | released |

**Who reset a cloud password?** 3c has a new bullet and a bundled query,
`password_reset_actor.kql`. `AzureAuditLogs` often leaves the initiator of a reset empty.
The Office365 copy of the same event names the actor: "Microsoft password reset service"
(self-service reset), an admin's UPN, or a sync account (the on-prem path). An SSPR reset
on an admin or service account is a finding in itself: anyone holding the account's SSPR
methods can reset a privileged password without MFA. The query runs on a ±10-minute window,
because `Office365` is the largest table.

Two runs on a Global Admin service account's ticket both wrote "no log names who
triggered the reset". The Office365 rows named the password reset service: an SSPR reset,
followed by single-factor browser sign-ins to the admin portals.

# 2026-10-28 — incident-investigation 1.6.0

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.6.0 | released |

**Actionable, separate from the verdict.** Step 5 now asks two questions: the outcome
(was the account compromised) and **whether the customer has to do something now**:
contain, undo or redo a change that did not hold, confirm one fact only they can, or fix
the setting that made this possible. A benign verdict can be actionable. The closure has
`verdict.actionable` and `verdict.customer_action`, the renderer shows "Action needed" or
"No action needed" on the verdict card, and the same two fields go to the portal's
`report_incident_verdict`. Actionable is decided on the risk the rule is about. Once that
answer is "nothing to do", the run stops; extra detail is optional.

This follows FluencyGPT's own first decision (`actionable`). On six re-runs FluencyGPT
flagged five as actionable and the agent closed all six benign. Only two needed the
customer to act (a disable undone by directory sync; a Global Admin service account reset
through SSPR), and in both the action was buried in the recommendation.

Needs portal 0.1.42 or later, whose `report_incident_verdict` takes `actionable`.

# 2026-10-28 — incident-investigation 1.6.1

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.6.1 | released |

**`has` matches whole terms.** Step 4's predicate-bug section now names the second usual
cause of a confident zero: a guest account `JBrown_contoso.com#EXT#@…` holds the term
`JBrown_contoso`, so `has "contoso"` misses it. Match a domain, part of a UPN or a file
name with `contains`. A 30-day scan written with `has` returned 0 rows in about 80 s; a
2-hour `contains` query then found the invites.

**A known partner is not actionable.** Step 5: a share or invite to an outside party the
tenant already works with is not actionable unless the content is sensitive. The signs are
earlier guests from the domain, invites by several colleagues on different days, mail folders
or projects named after them. The closure names that evidence instead of asking the customer
to confirm the relationship.

**Insider Risk alerts get their own evidence.** `file_movement.kql` now also reads the
`Endpoint` operations that take a file off a managed device: `FileUploadedToCloud` (with
its domain), `FileCopiedToRemovableMedia`, `FileCopiedToNetworkShare`, `FilePrinted`,
`FileTransferredByBluetooth`. For them the acting app is the program and the site is the
destination. 3f step 5: an Insider Risk or exfiltration alert names no file and no

domain is judged (most are the company's own apps), and the policy's base rate is reported
as tuning, never as the verdict. Two new verdict rows cover a personal or free-mail
destination (escalate as possible data theft) and no exfiltration rows (benign, not
actionable).

A blind run cleared a high-severity "Data Exfil to Unsanctioned Cloud" alert because 732
other users fired it that week, without reading what the user moved. That day the user had
no `Endpoint` exfiltration rows at all. Tenant-wide, the same day held 3,020 cloud uploads
by 538 users, 10,820 network-share copies, 1,519 prints and 164 removable-media copies, so
the branch does return rows when they exist.

# 2026-10-28 — aws-cloudtrail-activity-report 1.0.0

| Skill | Version | Status |
| --- | --- | --- |
| aws-cloudtrail-activity-report | 1.0.0 | new |

**AWS CloudTrail Activity report built only from the scheduled-report archive.** The skill never runs
`kql_search`, `run_report` or any live search: it checks `list_report_archive`, downloads the archived days,
merges them and writes HTML, PDF and CSV in the shared report layout (navy hero, KPI cards, tables).

- Merges dailies additively: trend rows summed, facet tables summed by value, a missing value is 0,
  the latest run is kept when a day was archived twice, `(other)` is events minus the listed values.
- A day that is not archived is a gap, listed on the page and drawn as a hatched column, never a zero.
- Shows events, errors, access denied, console logins, failed logins, logins without MFA, IAM changes,
  root-identity events and CloudTrail changes, with breakdowns by IAM event, root event, error code,
  service, region and identity type, plus archive coverage and script-hash changes.
- Counts only (no user names, addresses or ARNs); rows relate to NIST 800-53 controls and the report never
  claims compliance.
- `references/CloudTrail_Activity_Report.js` is the scheduled report that produces the archive.
- Tested on 27 archived days of the audit tenant (77.4M events).

# 2026-10-28 — microsoft365-entra-activity-report 1.0.0

| Skill | Version | Status |
| --- | --- | --- |
| microsoft365-entra-activity-report | 1.0.0 | new |

**Microsoft 365 and Entra Activity report built only from the scheduled-report archive.** The skill never runs
`kql_search`, `run_report` or any live search: it checks `list_report_archive`, downloads the archived days,
merges them and writes HTML, PDF and CSV in the shared report layout (navy hero, KPI cards, tables), like the
AWS CloudTrail activity report.

- Five sources in one report: Office 365 audit events, Entra user sign-ins, Entra directory audit,
  service-principal sign-ins and non-interactive user sign-ins, each with KPIs, daily charts, a daily table and
  breakdowns (operations, applications, countries, devices, error codes, credential types).
- Tolerates data the tenant does not have: the processor catches a missing table and records it in a `sources`
  table; the report shows each source as available, available with no events, partial, not available on this
  tenant or not collected, and never draws a missing source or a missing day as zero.
- Merges dailies additively (trend rows summed, facets summed by value, `(other)` is events minus the listed
  values for full-coverage lists); no distinct-user figures, because they cannot be summed across days.
- Counts only (no user names, addresses or object names); rows relate to NIST 800-53 controls and the report
  never claims compliance. Raw AzureAudit and MSEntra duplicate the parsed Entra tables and are not read.
- `references/Office365_Entra_Activity_Report.js` is the scheduled report that produces the archive
  (daily 04:00 UTC, archive on).
- Tested on 27 archived September days of the audit tenant (82,228 Office 365 events, 9,762 sign-ins, 9,015
  directory changes), with a simulated missing table and an older script version.


# 2026-10-28 — compliance-assessment 1.6.0

| Skill | Version | Status |
| --- | --- | --- |
| compliance-assessment | 1.6.0 | released |

**CloudTrail now comes only from the archive.** The five `ct_*` searches (events, console logins, IAM changes, root
events, errors) are gone. The skill reads the archived days of the scheduled report `CloudTrail_Activity_Report`
(`download_report_archive`, saved as `ct_archive.json`) and `build_report.py` sums the daily trend rows for the month.

- If the tenant has a CloudTrail table and no day of the month is archived, the skill stops the CloudTrail part and tells
  the user the archive is required (`--require-cloudtrail` makes the build exit 3 with that message). It never runs a
  CloudTrail search as a substitute, including `src_CloudTrail` and `history_CloudTrail`.
- Missing days are a gap, never zero: the source reads "CloudTrail (N of M days archived)" and the gaps section lists the
  missing days and the backfill.
- The CloudTrail facts in `compliance_summary.json` gain access-denied, logins without MFA, CloudTrail changes and the
  coverage fields (`days_archived`, `days_expected`, `missing_days`).
- Tested on the audit tenant: September (30 of 30 days) gives 79,450,291 events, 18 failed console logins, 14,245 IAM
  changes, 7,130 root events and 3,038,616 errors; October (27 of 31 days) is built with the four missing days listed;
  an empty evidence folder with `--require-cloudtrail` exits 3.
