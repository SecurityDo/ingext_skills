# 2026-10-23 — fluency-report-rollup 1.0.0 (new)

| Skill | Version | Status |
| --- | --- | --- |
| fluency-report-rollup | 1.0.0 | released |

**Monthly, quarterly and trend reports from a scheduled report's daily archive.** A scheduled
report with the archive enabled runs once a day for exactly the previous day. Each result is
kept for 12 months (platform 9.0.12, api 9.12.42). The skill assembles longer periods from
those dailies rather than running one long report.

- **Pipeline:**
  1. `list_report_archive` checks coverage: missing, aborted and running days, and script changes.
  2. `backfill_report_archive` fills gaps, if the user agrees.
  3. `processor_get` reads the script, to decide how each table merges.
  4. `download_report_archive` fetches up to 92 days per call.
  5. `scripts/rollup.py` merges them, and the result is spot-checked against `run_report`.
  6. fluency-report renders the page.
- **`references/merge_rules.md`:** covers each merge mode (sum, timebucket, top, aggregate,
  max/min/last, concat), lists what can't be merged (ratios, percentiles, distinct counts with
  no per-key table), and gives a worked check.
- **Two time-series traps found on real data:**
  - Metric range buckets are labelled by their end.
  - Each daily run also returns the bucket that straddles its start.

  Summing naively puts the per-day series off by about +4% and shifts it by a day.
- **Validated on titan:** `System_Event_Ingress_Report`, 30 backfilled days (2026-09-23 ..
  2026-10-22), compared with one direct 30-day run.
  - Every keyed total is within 0.02%.
  - The grand total is within 0.0002%.
  - The per-day series is within 0.001%.
  - The top-N orders are identical.
- The archive tools are only on tenants running api 9.12.42 or later. At release, that is
  titan only.

# 2026-10-23 — incident-investigation 1.4.4 → 1.5.0

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.5.0 | released |

**New workflow for fake IT helpdesk attacks (`references/workflows/helpdesk.md`).** Two real
intrusions in October were closed by the AI assist as "False Positive — incorrect alert
logic". On one, an employee installed a loader during a Teams call. On the other, Defender
saw hands-on-keyboard activity on the laptop. Fluency had raised incidents at risk 17,200
and 22,000; both were closed because the employee's sign-ins looked normal. In this attack
the attacker never signs in: they work through the employee's own computer during the
call. So the skill's default stance, "don't confirm a compromise that isn't there", led
it to the wrong answer.

- **H0 flips the burden for this family.** It lists the triggering rules and Defender
  titles: mail bombing, Teams impersonation after mail bombing, suspicious external Teams
  chat, Teams phishing, a Teams call reported by the user, `O365_Teams_OnMicrosoft_Tenant_Chat`,
  `O365_Endpoint_Download_From_Azure_CloudApp`, and hands-on-keyboard / human-operated /
  emerging-threat alerts on a user who had an outside Teams contact that day. Clean sign-ins,
  MFA and mailbox clear nothing here.
- **H1–H5:**
  - H1: the Teams contact and whether the employee engaged (answered, accepted, replied).
    Call records arrive about four hours late.
  - H2: mail bombing before the contact. Covers gateway blind spots and KnowBe4-style
    simulations.
  - H3: what ran on the device during and after the call. Reads endpoint downloads,
    `processCommandLine` in the Defender alert evidence (the lure URL is only there),
    `MsiInstaller` 1040/1033 and PowerShell 400 in `WindowsAudit` (local time), and the EDR.
  - H4: containment already done (disable, ConfirmAccountCompromised, token revocation,
    password reset, MFA re-registration). A Defender "contained user" block after a new
    laptop joins is often the employee's own work.
  - H5: the same sender's other contacts in the tenant.
- **H6 verdict table:**
  - Anything ran on the device: Confirmed.
  - A call answered: Escalate.
  - Benign only for contact-only cases, with controls.
  - Never "incorrect alert logic".
- **Four bundled queries,** validated and run against the source incidents:
  - `teams_external_contact.kql` found the outside chat and the 5 min 33 s call, with the
    device.
  - `teams_external_census.kql` listed exactly the 13 attacker senders on the second
    incident's tenant (9 tenants, 27 employees reached) and no legitimate partner.
  - `mail_bomb_hourly.kql` found 55 and 46 flagged messages in two consecutive hours,
    45 minutes before the chat.
  - `endpoint_activity_window.kql` found the MSI download from a `cloudapp.azure.com`
    host during the call.
- **SKILL.md:**
  - A short stance paragraph after "Never write a verdict from the summary alone".
  - A routing-table row for the new workflow.
  - A step 5 rule restricting the verdicts available for this family.
  - The Assets entry.
- **Cross-references:** `office365.md` and `generic.md` route these tickets to the new
  workflow.
- `cowork/incident-investigation.skill` rebuilt.

# 2026-10-23 — endpoint-os-currency 1.0.0 (new)

Ported from the Fluency companion app (`fluency-mcp4mssps`, `endpoint-os-currency`), reworked to
run on the tenant connector's own tools instead of the MSSP `falconOsCurrency` FPL report.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| endpoint-os-currency | 1.0.0 | released |

## What changed

- New skill (in `reports/`): endpoint OS currency and end-of-support report. It reads one resource
  dump via `get_resource_dump_url` (`falconAgent`, else `sentinelOneAgent`, else `office365Device`)
  and `scripts/build_report.py` evaluates it locally, writing HTML and a per-host CSV.
  `scripts/render-html-pdf.mjs` renders the PDF.
- Two axes kept apart: support status from a curated, dated Windows lifecycle table (Home/Pro vs
  Enterprise/Education dates; builds shared by a client and a server release show as "verify"),
  and build currency against the newest build seen in the fleet.
- Falcon dumps give edition, server vs workstation and patch revision; SentinelOne gives the
  build number only; Entra gives OS and version only, so it is the weakest source.
- A build newer than the table is treated as supported and cannot set the fleet's newest build.
- First runs: one tenant per source (Falcon, SentinelOne, Entra devices) on the Develop connector.

# 2026-10-23 — health-status-report 1.1.0 (new)

| Skill | Version | Status |
| --- | --- | --- |
| health-status-report | 1.1.0 | released |

**Installed-application health for one tenant, using the Fluency 9 Applications page logic.**
Each installed application instance is Running, Error, Attention or Other, decided the way the
page decides it: connector state, errors and error states, traffic through the application's
sources and sinks in the last 24 hours, whether its components exist, and whether each has been
active. Error bytes are shown per component and, as on the page, do not change status.

- **Inputs:** one `list_connector_config` call returns the installed applications with live
  components, errors, last-active times and hourly byte counters. `list_resource_dumps` is optional
  (freshness of resource sources). `scripts/build_report.py` evaluates them locally and writes
  HTML and a per-application CSV; `scripts/render-html-pdf.mjs` renders the PDF.
- **Credentials:** the call returns credentials in clear text. `scripts/scrub_config.py` reduces
  it to names, ids, types, state, errors, last-active and byte totals, and the raw file is deleted.
- **Not available:** a disabled flag, so the Disabled status is not produced.
- **Needs** a connector where `list_connector_config` is deployed. First run: the Develop tenant
  `kql`.
