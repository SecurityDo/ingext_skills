# 2026-10-04 — incident-investigation 1.2.19 → 1.2.20

Read the customer's Azure Log Analytics workspace when one is connected. On a stolen-session
ticket, trace the session to where it was minted, and never call the incident contained
until a password change has reached Entra.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.2.20 | released |

## Why

A Defender "Possible use of a stolen session cookie" ticket was investigated on the datalake
alone. The account's real source was an `AzureLogAnalytics` integration, which
`list_data_tables` does not show and the skill never mentioned. The run reached "real
compromise, contained in 71 minutes". A SOC analyst working from the same workspace found
four things that run missed. All four were one `azure_logs_search` away:

- **The session was captured the day before.** A relayed sign-in (correct password plus an
  SMS code, from an address and OS that were not the user's) minted the session. It was
  replayed 21 hours later. The datalake's `AzureSigninLogs` held 9 of the ~20 sign-ins in
  that hour and none of the non-interactive ones.
- **The attacker pulled the directory.** Graph `GET /users?$top=999` came from a scripted
  client, followed by a `$search` for payroll, finance and HR staff. Graph requests exist
  only in `MicrosoftGraphActivityLogs`.
- **The password was never rotated in the cloud.** The on-prem reset used "must change at
  next logon", so it was not synced. The attacker came back twice with the correct
  password and was stopped only because nobody approved the push. On-prem resets appear only
  in `IdentityDirectoryEvents`.
- **Three mailbox items were read, not one.** A `substring()` on the `Folders` list hid the
  other two.

Every new query below was run unmodified against that ticket. Together they reproduce the
analyst's capture, replay chain, directory dump, payroll search, unsynced reset and
post-containment password attempts.

## Changes

- **SKILL.md step 0, "Find every source":** probe `azure_logs_list_tables` /
  `azure_logs_get_schema` on every account. Where the workspace has a table, it is the source
  for that question. Notes on the dialect: the time range is ANDed and defaults to 24h;
  `first` and `last` are reserved words. The `azure_logs_*` tools are added to the tool table.
- **Six bundled workspace queries** (run with `azure_logs_search`):
  - `la_signin_summary`
  - `la_signin_detail`
  - `la_session_trace`
  - `la_graph_activity`
  - `la_password_events`
  - `la_post_containment`

  New placeholders: `{SESSION}`, `{OID}`, `{TCONTAIN}`.
- **office365.md:**
  - A table mapping each check to its datalake or workspace query.
  - New **3a′ — Trace the session**: the first row is the capture, so read what preceded it.
  - Two new 3c checks: **"Is it contained?"** (a revoked session is not a changed password;
    unsynced must-change resets; any post-containment "Correct password" from a non-user
    address means not contained) and **Graph reconnaissance**.
- **Step 3 routing:** Defender alerts about a user's session or token now route to the
  Office365 workflow.
- **generic.md:** read the raw `MSDefenderAlert` `evidence[]`, because the behavior summary
  drops it. An AI assist that saw only the summary closed this ticket as a false positive.
- **Bounded queries:** never `substring()` a list column. Expand it.
