# 2026-10-05 — incident-investigation 1.2.20 → 1.2.21

Read who signed a SentinelOne detection before judging it, attribute behavioural
indicators to a process before citing them, and do not call a response finished while
it waits for a reboot.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.2.21 | released |

## Why

A SentinelOne "Ransomware" detection (behavioural engine, suspicious confidence) on an
office-suite web installer was closed by an automated run as **confirmed ransomware,
fully contained**. The run had the threat record, and it missed four things that change
the verdict:

- **The file was signed by the vendor.** `publisherName` named the vendor,
  `fileVerificationType: SignedVerified`, `isValidCertificate: true`. The closure never
  mentioned the signer.
- **The product was already installed on four other hosts,** at four different versions.
  The app census would have shown this, but it runs only when the rule names a product.
  Here the file name and the publisher did.
- **The response was not finished.** Remediate and rollback were `pending-reboot`, and 3
  rollback actions had failed. The run wrote "kill, quarantine, remediate and rollback all
  completed".
- **The indicators came from the whole storyline.** The record carried persistence and
  shell-extension indicators an installer explains. It also carried SAM, Kerberoasting
  and browser-memory indicators that an installer does not obviously explain. Those are
  the real open question, and the run cited neither group.

Two smaller errors: the run treated the MDR's `true_positive` verdict as independent
confirmation, and it said the AI-assist had closed the ticket. In fact an analyst closed
it as a true positive first, and the AI-assist overwrote the classification three minutes
later.

## Changes

- **sentinelone.md S1:** fall back to the threat record in the index on "alert not found"
  as well as on "no integration". Unified Alerts can be far sparser than threats.
- **sentinelone.md S2:**
  - The signer fields (`publisherName`, `certificateId`, `fileVerificationType`,
    `isValidCertificate`) are required in every closure.
  - New "Who signed it": a valid vendor signature routes to the installed-product check
    before any verdict, and a behavioural "Ransomware" label on a signed installer is
    named as a common false positive.
  - New "Behavioural indicators belong to the storyline": attribute each indicator to a
    process, group them as explained or not explained by the install, and make the
    unexplained ones the escalation question.
  - New "Is the mitigation finished?": per-action `status` and `actionsCounters`, and
    `rebootRequired`.
  - New "An analyst verdict from the customer's MDR is a relayed claim".
- **sentinelone.md S4:** the app census triggers when the rule, the `publisherName` or the
  file name names a product.
- **sentinelone.md verdict shapes:** two rows for the signed-installer case, depending on
  whether every indicator is explained by the install.
- **SKILL.md step 1:** read the ticket's comment history in order, with who made each
  change. The final classification can be an AI-assist overwriting a person.
- **SKILL.md risk score:** the reputation dimension (`VT_MALWARE` / `REPUTATION_FILE` 1000,
  `VT_POSITIVE` / `VT_UNKNOWN_HASH` 500, from `fsbv2/risk/risk_config.json`) and a
  worked 12800 example.
- **SKILL.md step 2:** name the base-rate keys in the closure, not just their count.

# 2026-10-05 — incident-investigation 1.2.21 → 1.2.22

An outbound-spam check: when Exchange restricts a mailbox for exceeding its sending
limit, find what actually submitted the mail before treating it as a takeover.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.2.22 | released |

## Why

A shared mailbox hit the 10,000-recipients-per-24h limit and was restricted. The AI assist
recommended blocking sign-in and resetting the password. Two investigations found no
takeover. One of them stopped at "who sent the mail is not visible here". The answer was
in the firewall: no cloud sign-ins and no Send audit from the mailbox, while an on-prem
relay sent SMTP to the Microsoft mail edge all day.

The same case showed the check's main trap. The relay's volume first read as "five times
normal". That figure compared a Monday against a weekend; against the previous week's
working days (547–1,314 connections a day) it was ordinary. A 170 MB session at 04:00 that
looked like the burst recurred every day.

## Changes

- **office365.md 3d — Outbound spam: find what actually sent the mail:**
  - the census of restrictions;
  - whether the mail went through the mailbox (a zero next to many senders is the relay,
    not necessarily "auditing disabled");
  - what the sign-in feed can see (SMTP AUTH is non-interactive);
  - which internal host sent it, its weekday baseline and its hourly shape, named from
    domain logons;
  - what the firewall cannot attribute;
  - a sync-wave census before reading a `LastDirSyncTime` change;
  - three verdict shapes.
- **Six new bundled queries,** each run against the case above:
  - `sending_limit_census`
  - `send_audit_ctl`
  - `signin_coverage_ctl`
  - `fw_smtp_senders`
  - `fw_smtp_sender_baseline`
  - `fw_smtp_sender_hourly`
- **SKILL.md step 3:** the Office365 routing row names 3d.
