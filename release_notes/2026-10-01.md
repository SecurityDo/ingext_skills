# 2026-10-01 — incident-investigation 1.2.9 → 1.2.10, ingext-kql 1.0.6 → 1.0.7

A host name is not a machine, and a forwarded Windows `timestamp` is not the event time.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.2.10 | released |
| ingext-kql | 1.0.7 | released |

## Why

An `asset_…` ticket on a production server scored high for an audit-log clear, four
log clears, local domain groups removed and a sysprep restart. The investigation
escalated it with one question: was the sysprep on the production server authorized?
It was not the production server. A clone of it, still reporting the original's
Hostname, did all of it before sysprep renamed it. The production server served its
users all day. Every check in the procedure reads "the host" by its `Hostname`, so
two machines' events were judged as one. The renamed clone raised its own ticket the
same day and was investigated separately; that run found the rename but could not
correct the first.

The same run timed the log clear 80 minutes late. On `WindowsAudit`, `timestamp` is
stamped when a record reaches the platform. The clone's backlog arrived in one
second, so its events landed ahead of events they actually followed. The second run
also reported a "VM clock ~40 minutes ahead" side finding. That was the host's local
`EventTime` zone plus the delivery delay.

Measured on the tenant concerned (identifiers removed):

- `['@sender']` split the host into two addresses: 103k events from the original,
  13.5k from the clone. The clone's records start at the same `RecordNumber` and stop
  below the original's, and its last event is the sysprep restart.
- Domain-controller logons map address to computer account from inside the events:
  in the 30-hour window measured, the original's `NAME$` authenticated only from its own address. The clone first
  authenticated after its rename and join, under its new name.
- The emitting lsass `ProcessID` differed (1088 vs 968), but a services.exe PID
  coincided across the two, so it is a hint only.
- A bare `@sender` in KQL returns null; `['@sender']` works. The `lake_search` facet
  on `@sender` answers in about 8 s. The KQL split takes about 67 s on that host, past
  the 60 s point where an MCP call can return empty.

## What changed

incident-investigation:
- `SKILL.md` step 4: two new traps. "On a forwarded Windows feed, the raw `timestamp`
  can be late too": order on `EventTime` (convert the zone) and `RecordNumber`, and
  never report the zone offset as clock skew. "A hostname is not a machine": facet
  `@sender` before judging any `asset_…` ticket, attribute events per sender, name
  each address from DC logons, and treat PIDs as a hint.
- New `assets/queries/host_senders.kql` and `host_ip_owner.kql` (±24h, deduped by
  aggregation, `take 1000`). New `{HOST}` placeholder.
- `references/workflows/generic.md`: G1 checks for one machine first on `asset_…`
  tickets; G4 uses `EventTime`/`RecordNumber` on forwarded Windows feeds.

ingext-kql (source: `ingext_schema`, `datatypes/WindowsAudit/`):
- `info.yaml`: a collector-envelope section (`@sender`, `@source`, `@collector`,
  bracket-quoted). Corrected `timestamp` (arrival time, not derived from
  `EventTime`), `EventTime` (host-local, no zone), `Hostname` (a name, not an
  identity), `RecordNumber` (unique per machine + channel; clones reuse numbers; a
  1102 does not reset it) and `ProcessID` (per-boot fingerprint).
- New worked queries `wa-hostname-senders.yaml` and `wa-host-identity.yaml`.
- Only the WindowsAudit entry was synced into `manifest.json`. A full
  `sync_schemas.py` run also drifts other tables and deletes the hand-added `ASSET`
  table, so that resync is left for its own change.
- The rebuilt package now also carries the GuardDuty schema, which was committed
  but missing from the stale `cowork/ingext-kql.skill`.

## Verification

- Both bundled queries and both worked queries were run on the tenant above and
  returned the split described; all parse.
- `scripts/validate_skills.py --worktree` passes; both `cowork/*.skill` packages rebuilt.
- No customer identifiers added (sample output uses documentation addresses and
  placeholder names).

# 2026-10-01 — ingext-kql 1.0.7 → 1.0.8

`sync_schemas.py` keeps the fixed system tables.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| ingext-kql | 1.0.8 | released |

## Why

A full resync deleted `references/schemas/ASSET/`. The script rebuilt the whole
`references/schemas/` tree from `ingext_schema`, and `ASSET` is a fixed system table
with a hand-maintained schema and no datatype there. So nobody could run the sync
without hand-repairing the result, and the embedded KB drifted (Netskope missing,
F5 / Meraki / FortiGate edits unsynced).

## What changed

- `scripts/sync_schemas.py`: a `FIXED_TABLES` list (`ASSET`). A sync builds into a
  staging directory beside `references/schemas/`, copies each fixed table's folder over
  verbatim, then swaps it in, so a failed build no longer leaves the skill without
  schemas. Fixed tables stay out of `manifest.json`, and `--check` ignores them. If
  `ingext_schema` starts defining a fixed table, sync and `--check` both stop with an
  error naming it, rather than keeping two copies.
- `SKILL.md`: the fixed-tables note says a new fixed table goes in `FIXED_TABLES` too.

## Verification

On a scratch copy of the skill: `--check` reported stale before the sync and up to
date after it; `ASSET/` was byte-identical after the sync and absent from the manifest;
the swapped-in directory kept mode 755 and no staging directory was left behind.
Defining `ASSET` in a scratch `ingext_schema` made both modes exit 1 with the error.
`scripts/validate_skills.py --worktree` passes; `cowork/ingext-kql.skill` rebuilt.

The pending full resync itself is NOT in this change.

# 2026-10-01 — incident-investigation 1.2.10 → 1.2.11

A static engine's indicators say what a file can do, not what it did. And the order of a file's copies decides whether it arrived or left.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.2.11 | released |

## Why

An automated run closed a SentinelOne ticket as `confirmed` malicious and recommended
isolating two hosts. The evidence was the threat record's `indicators[]`, which it read as
"a dropper/stealer behavioral profile". Every one of those indicators was a capability
the on-write static engine read from the binary ("File can delete files", "can create
processes", "can delay its execution", high-entropy sections). The file was a compiled
Python executable, and a packaged Python app carries most of those indicators by
construction. Nothing in the record was an observed action. The run also cited
`classificationSource: Behavioral` and a `detectionType: dynamic` stamp as proof of
behaviour. The same hash, judged by the same static engine, carried `dynamic` on one
record and `static` on another.

## What changed

- `references/workflows/sentinelone.md` S2: new rule. Indicators under a static engine are
  capabilities, not behaviour. Decide static or dynamic from the engine. The rule lists
  what counts as behaviour, and says a capability list never supports `confirmed` on its
  own.
- The S2 fields table now classes `On-Write Static AI` / `On-Write DFI` as static,
  whatever `detectionType` says.
- New verdict-shape row: an unsigned executable that named users launched, flagged only by
  the static on-write engine, escalates with the question "does the organisation
  recognise the file?"
- S4: new "Arrival or departure" rule. The same run called the file "consistent with
  email-attachment delivery" because some copies sat in Outlook and WebView2 attachment
  caches. Every one of those copies appeared minutes after the user launched the file
  from `Downloads`, so the file was being attached and sent. Order a host's copies by
  `identifiedAt` before naming a route. Only the earliest copy can show arrival, and a
  copy after a launch is the file leaving. `Downloads` alone does not name a source, and
  a launch as the earliest record means the arrival is a gap. The old Origin bullet
  equated `Downloads` with a browser download and is replaced.

# 2026-10-01 — incident-investigation 1.2.11 → 1.2.12

A hash hit on a cached installer is an installed product. Name it from the inventory and count it across the account before you treat it as one host's malware.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.2.12 | released |

## Why

An automated run escalated a CRITICAL STAR hash alert. The alert came from a custom rule
for a public supply-chain campaign. The rule had matched a file at rest in
`C:\Windows\Installer` during an agent's first full disk scan. The run established that
nothing ran, but it could not say what the file was: it had no external hash lookup, and
the file's cache name is meaningless. So it escalated on "hash unverified". It never
queried `sentinelOneApplication`, because S4 only asked for an install census when the
detection was a *named* application. The inventory named the product: it was installed on
the subject host and across much of the account, at a version released after the fix for
the campaign the rule targets. That moves the finding from the host to the rule's hash
list.

The same review hit a second trap: a free-text search for a word in the rule's name
returned 0 across the whole index while the ticket's own alert was in it.

## What changed

- `references/workflows/sentinelone.md` S1: STAR alerts have no threat record. The matched
  file, its hashes, the event type (`FILESCAN` = at rest) and the actor are in the alert's
  `3608` activity under `@sentinelOneActivity.data.*`.
- S4, new "Is it an installed product?" section:
  - Two signs that a hash hit is an installed product: the rule names a product, or the
    file sits in the Windows Installer cache. The cache explained: installed, dormant,
    and outside the arrival-route analysis.
  - Four steps: probe the inventory, name the package on the host, census it, then compare
    the installed version with the range the rule targets.
  - One alerting host among many is expected, because scans reach the file at different
    times; say it is a gap rather than evidence.
- The old probe note ("on some tenants it returns only a `timestamp` column") is replaced.
  That is what `take 1` with no `project` returns on any tenant, because the engine
  returns only the columns a query names. It never meant the table was unreadable.
- Search-the-index note: count alerts by name with a filter on `@sentinelOneAlert.name`,
  never free text, and use the ticket's own alert as the control.
- New verdict-shape row: a STAR hash hit on a cached installer whose inventory version is
  outside the rule's range is benign for the host, with tuning in the console. Inside the
  range, it is a fleet exposure.
- New bundled queries: `s1_app_probe.kql`, `s1_host_apps.kql`, `s1_app_census.kql`
  (placeholders `{HOST}`, `{APP}`). All three parse-validated and run against a live
  account.

# 2026-10-01 — incident-investigation 1.2.12 → 1.2.13

Run the inventory queries as bundled, leave `searchStr` empty when a filter does the selecting, and say when a product was named from the inventory alone.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.2.13 | released |

## Why

A re-run of the ticket behind 1.2.12 reached the right verdict, but it took a longer route
in three places:

- **It hand-wrote the inventory queries instead of running the bundled ones.** It guessed
  the host column as `computerName`, and `validate_kql` accepted that because the validator
  does not check column names. The query came back with no columns and no rows. Several
  calls of column guessing followed before it found `agentComputerName`, the column the
  bundled queries already use.
- **It put the alert name in `searchStr` as well as in the exact-name filter.** The two
  are ANDed, so the free-text term brought back the false zero that 1.2.12 warns about.
  It recovered on the next search.
- **Its closure named the product without saying the hash was never checked externally.**

## What changed

- `references/workflows/sentinelone.md`, alert-name census: the example now uses
  `searchStr: ""`. An empty string matches everything, like `"*"` or omitting the field.
  New note: a free-text term next to the filter brings the false zero back.
- S4 "Is it an installed product?":
  - Run `s1_app_probe` / `s1_host_apps` / `s1_app_census` as bundled before writing your
    own (non-negotiable 4).
  - The host column is `agentComputerName`. `computerName`, `hostName` and `assetName` are

  - `validate_kql` passes unknown columns, so an empty result from a hand-written query
    proves nothing.
- S4 step 2: without an external hash lookup, the verdict sentence and the closure's gaps
  say the identification came from the inventory alone. A version range recalled from a
  public advisory is background knowledge, not a measured finding.

# 2026-10-01 — incident-investigation 1.2.13 → 1.2.14

On a consent ticket, work out whose app it is, what the grant says, who asked for it, and what the app did as each user.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.2.14 | released |

## Why

An automated run of an admin-consent ticket reached the right outcome (escalate, not a
takeover), but four parts of its reasoning were wrong or missing:

- **It said the admin "self-registered" the app and recommended rotating its secret.**
  The audit showed "Add service principal." and no "Add application.". The app was a
  third-party multi-tenant app; the vendor owns its credentials, so the tenant has no
  secret to rotate. The reply URLs named the product.
- **It reported no follow-on activity, while the app had already written to another
  user's mailbox.** The grant was delegated. The run checked only
  `ServicePrincipal_<spid>` actions (`app_actions_o365.kql`), and delegated actions are
  recorded under the user, with the app in `ClientAppId` / `AppAccessContext`.
- **It never found who asked for the app.** A non-admin user had been blocked with
  `AdminConsentRequired` minutes before the admin consented.
- **It reported MFA state as unavailable**, although the `Update user.` row at the sign-in
  showed an already-enrolled authenticator approving it.

Later the same day a second administrator widened the grant to Teams chat and channel
read and send scopes. A run started before that cannot see it, so a final census is
needed.

## What changed

- `references/workflows/office365.md` 3c, application checks:
  - **"Whose app is it?"** Your own registration and a third-party multi-tenant app call
    for different remediation. Name the vendor from `AppAddress` and treat the publisher
    as unverified until the snapshot confirms it. The levers are the grant and the
    service principal.
  - **Read the consent whole:** `IsAdminConsent`, `OnBehalfOfAll` / `AllPrincipals`,
    `IsAppOnly`, and `ConsentAction.Reason` ("Risky application detected" means
    Microsoft flagged the app and an admin overrode it).
  - **Find who asked:** `AdminConsentRequired` / `DelegationDoesNotExist` sign-ins to the
    app before the consent.
  - **Re-run the consent census at the end.** A remove-then-add pair is how Entra records
    a scope change on an existing grant.
  - **New delegated-use check** for `IsAppOnly: False`, with its control. Most reads are not
    audited, so a zero covers writes and sign-ins only.
- 3b: when a sign-in precedes the flagged action in a non-authentication ticket, read the
  `StrongAuthenticationPhoneAppDetail` diff on the `Update user.` row. An unchanged enrolled
  device is cheap, strong evidence against a takeover.
- New bundled queries: `app_delegated_use_o365.kql` and `app_delegated_use_ctl_o365.kql`
  (placeholders `{APPID}`, `{WFROM}`). Both were parse-validated and run against a live
  account. On their first run they found the write to another user's mailbox and the
  blocked requester.
