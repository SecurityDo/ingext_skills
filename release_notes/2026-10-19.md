# 2026-10-19 — incident-investigation 1.2.24 → 1.3.0; ingext-log-analytics-evidence 1.0.0 (new)

The checks that read a customer's own Azure Log Analytics workspace move into a sub-skill,
and they now cover endpoint and Azure-resource tickets as well as sign-in ones.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.3.0 | released |
| ingext-log-analytics-evidence | 1.0.0 | new |

## Why

**The workspace checks were sign-in-only.** A Defender for Endpoint custom detection
("service accounts performing remote PowerShell") fired on the four nodes of a hybrid
cluster within one minute.

- Each ticket was scored as a first-seen asset.
- The AI assist closed each one as "no supporting telemetry". It had read only the
  alert. A custom detection's alert evidence names only the machine, and the rule's
  query lives in the customer's Defender portal.
- The customer's Log Analytics workspace held what the alert lacked:
  - **The trigger.** The alert's `firstActivityDateTime` matched one `DeviceEvents`
    PowerShell row to the 100 ns. It was the cloud platform's own remote-support
    bootstrap script, running as SYSTEM, 31 s after the node was onboarded.
  - **The remote sessions.** `DeviceLogonEvents` showed they came only from the
    cluster's seed node.
  - **Who did it.** `AzureActivity` named the administrator who deleted and rebuilt
    the cluster's resources that evening. That administrator's sign-ins passed MFA and
    carried no risk.
- The rebuild also explained the first-seen score: a reimaged node gets a new Defender
  device id.

The skill's step-0 workspace probe mentioned only the sign-in tables, so nothing pointed
an endpoint ticket at the workspace.

**Few accounts have a workspace.** The workspace material was spread through
incident-investigation's SKILL.md, office365.md and generic.md. Every run on every
account read it, although almost none could use it. A sub-skill keeps it out of the way
on those accounts. It also keeps the step-0 question, so the account that does have a
workspace is still caught.

## Changes

### ingext-log-analytics-evidence 1.0.0 (new)

- **Step-0 probe and schema call.** This covers when the skill applies at all.
- **Why the workspace wins over the datalake**, table by table.
- **Dialect traps:**
  - The time range is ANDed with the query's own filter, and a missing range means the
    last 24h.
  - `first` and `last` are reserved words.
  - The union of the two sign-in tables needs `DeviceDetail` normalised first.
  - **New:** `SigninLogs` re-emits a row, with the same `Id` and `CreatedDateTime`,
    each time its risk state changes. Count distinct `Id` and order on
    `CreatedDateTime`.
  - **New:** a capture row's failure code does not mean no session was minted.
- **Office365 checks**, moved from office365.md: the sign-in profile and detail (3a),
  the session trace (3a′), "is it contained?" (3c) and the Graph check (3c).
- **Endpoint and Azure-resource checks** (G1 / G4 / G5):
  - **What the alert fired on.** `la_device_trigger`, keyed on `firstActivityDateTime`;
    the row with `AtT0 = true` is the trigger. Also reads `firstSeenDateTime`.
  - **Who made the change.** `la_azure_activity`, then the caller's sign-ins, then
    `IdentityDirectoryEvents`.
  - **Who logged on, and from where.** `la_device_logons`.
- **Nine bundled queries.** The six existing `la_*` sign-in and containment queries move
  here unchanged. Three are new: `la_device_trigger`, `la_device_logons` and
  `la_azure_activity`. The workspace-only placeholders move with them: `{SESSION}`,
  `{OID}`, `{TCONTAIN}`, and the new `{AZRES}`.

### incident-investigation 1.3.0

- **Step 0:** one `azure_logs_list_tables` call on every account and every incident type.
  - "No AzureLogAnalytics integration" (the usual answer) means nothing else changes.
  - A listing hands off to the sub-skill.
- **"Depends on"** lists the sub-skill, used only when the workspace exists. If the
  workspace exists but the sub-skill is not installed, every check it would have
  answered is a gap in the closure, never a datalake negative.
- **office365.md and generic.md** keep the reasoning: why a session matters, why a
  revocation is not a password change, why a custom detection's alert is empty. Each
  workspace step is marked *workspace* and points at the sub-skill.
  - Each also says what to record without a workspace: "session origin not
    established", "post-containment sign-ins not verified", "trigger not verified".

## Verification

- **Skill validator:** passes for both skills.
- **New queries:** all three validated against a live workspace and ran on the case
  above.

| Query | Result |
| --- | --- |
| `la_device_trigger` | Exactly one `AtT0` row: the SYSTEM `Start-Transcript` at the alert time |
| `la_device_logons` | 146 rows. Every remote source was a cluster node, a cluster network address or loopback |
| `la_azure_activity` | Parses. A query of the same shape returned 178 rows naming the administrator |
