# 2026-09-17 — new skill: deploy-fpl-processor

One new skill. `deploy-fpl-processor` takes an FPL processor from a repo to a tenant through
the provider proxy and wires it into the tenant's running pipeline. It came out of deploying
`Varonis_Behavior` to a customer tenant, and it encodes what that deploy got wrong the first
time.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| deploy-fpl-processor | 1.0.0 | released |

## Implementation notes

- **The mapping is validated against the target tenant's own records before anything is
  wired.** This is the step the skill exists for. The Varonis processor passed 9 local
  fixtures and would still have emitted zero asset signals on the target: the tenant writes
  assets as `<resource>(<data source>)` — a drive on a file server, a domain on a directory
  source — and the parser only understood UNC paths. The same pass found a `severityId` of `3`
  (Informational) that was not in the severity mapping. Neither is discoverable from a vendor
  sample; both took one KQL projection and one `processor test` against a rebuilt real event.

- **Wiring goes through a client library, never a hand-built request.** `assets/ingext-pipe.mjs`
  drives the `ingext-api` TypeScript client (`~/cc/ingext_api/typescript`): `wire` creates the
  redis sink on `queue:BehaviorSummary:EventQueue` and the pipe on the existing application
  router, `unwire` removes them, `list` prints the topology. It is idempotent, refuses to wire
  a processor that is not deployed, will not delete a sink another pipe still uses, and reads
  the pipe back after writing it.

- **Both client libraries were extended rather than worked around.** Three gaps turned up and
  all three are now closed upstream in `~/cc/ingext_api`:
  - the TS client had no `gridAccount`, so it could not reach a tenant through a provider at
    all — added to `client.ts` and the `Ingext` facade, with three tests;
  - `StreamPipeConfig` had no `priority` or `tags` in either the TS types or the Go model, so
    any pipe built from those structs came out `priority: 0` and untagged, unlike every
    app-installed pipe;
  - the Go CLI had no `add-pipe`, `del-pipe`, `del-router` or `list-router`, and `add-sink`
    could not make a redis sink — all added to `internal/commands/stream.go`.

- **The return status is documented, because getting it wrong is silent.** A router stops at
  the first pipe that does not return `"abort"`, and `"abort"` skips that pipe's own sinks —
  so a behavior pipe added behind a `"pass"`-returning `Plugin_Passthrough` receives nothing,
  and the symptom is indistinguishable from a connector that has not polled yet. The skill
  carries the four-status table (`pass` / `abort` / `drop` / `error`), the
  `Platform_Sink("", {obj})` + `return "abort"` pattern, and the instruction to check the
  upstream pipe before wiring rather than after. The same table corrects the `fpl-processor`
  skill in the Scripts repo, which had `pass` and `abort` the wrong way round.

- **`platform_event_tail` replaces waiting.** `{id: "pipe_xxxx", status, limit}` returns the
  most recent events one pipe ended with, in a separate buffer per status, so a freshly wired
  chain is verified against whatever traffic is already moving instead of against the vendor's
  next alert. On the Varonis rollout it showed the upstream pipe's events under `abort` and
  the same events on the new pipe under `drop` — the whole contract, minutes after wiring,
  with the next alert still hours away. A new pipe empty under *every* status is the signature
  of an upstream `"pass"`, not of a quiet connector.

- **Releasing is a separate act from deploying, and the skill says so.** Deploying puts an
  object on one tenant; `ingext import` installs from the repo's
  `<resource>_release.json` / `_dump.json` registries, which only `sync_cli release` writes.
  An object committed but never released reaches nobody, and a template naming an unreleased
  processor cannot install at all. The section carries the run order (commit, then release,
  then commit the registries as `release`), the four things that decide whether an object is
  picked up — a `meta/` entry, an id taken from the registries, a `gitPath` pointing at its
  own file, and a terse commit subject, since `lastComment` is the whole commit message — and
  the entry-by-entry diff to run before committing.

- **Read the sibling app, don't invent the shape.** A tenant already running Falcon or
  MSDefender behavior signals has an authoritative pipe and sink to copy. `platform_router_dao`
  has no `list` action, so `platform_list_configs` is the one inventory call worth knowing.

- **Small KQL traps, for the time they cost:** `$__timeFilter` is not KQL here (use
  `where timestamp > ago(7d)`), and `| take 1` returns only the columns the query mentions, so
  every field the processor reads has to be projected explicitly.
