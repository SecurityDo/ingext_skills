# 2026-09-28 — incident-investigation 1.2.1 → 1.2.2

Every query is now bounded before its result reaches the model: at most the last
**30 days**, at most **1,000 rows**, with raw rows **deduplicated in the query**.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.2.2 | released |

## Why

An Agent Portal chat investigating one administrator ended in "Prompt is too long".
The model validated eight queries, then ran seven of them in one turn. Three came back
as 30 days of raw rows with nested columns (`TargetResources`, `ModifiedProperties`).
Each MCP tool result is truncated at about 25,000 tokens, and several near-limit results
in one turn overflowed the model's context. The conversation cannot recover from that.

Measured on the same account afterwards. The directory-audit query
(`dir_changes_targeting`) returned **981 rows, about 2 MB — and only 35 distinct**. Every
event came back about 28 times with identical values, `TimeGenerated` and
`CorrelationId` included.

The skill also said an oversized result "is saved to a file; read it there". On the
Agent SDK the portal runs, it is not. The result is truncated, with an
`[OUTPUT TRUNCATED - exceeded 25000 token limit]` notice. That line is corrected.

## What changed

- **New non-negotiable (7): every query is bounded.** 30 days, 1,000 rows, raw rows
  deduplicated in the query. A result that hit a bound is partial. The closure says so,
  and the window is narrowed rather than widened. "Use 30 days" is now "never more than
  30 days".
- **All 17 bundled queries are capped.** Raw-row queries end in
  `top 1000 by <time> desc` then `order by <time> asc`: the newest 1,000 rows, still in
  time order. A `take` after an ascending sort would have kept the oldest. Aggregates and
  snapshot lookups end in `take 1000`.
- **The 10 raw-row time-series queries dedupe in the query.** Every non-time column
  goes through `tostring()`, then `summarize dups = count() by` all of them. That is an
  exact distinct that keeps every column; `dups` is each row's copy count. The three
  snapshot lookups need no dedup: they return one row per object, measured at 1 row for
  a user from a 26-row table.
- **New section "Bounded queries"**, for the queries the model writes itself:
  - time and row limits
  - the dedup pattern, with a parse-checked example
  - the engine's dedup traps (see below)
  - what to do when a bound is hit
  - run wide raw-row queries one or two at a time, not all together
- **The duplicate-rows trap is updated.** The bundled queries now dedupe. Count events,
  not `dups`. A `summarize count()` over raw rows elsewhere is still inflated.

## Engine traps found while writing it

- `distinct *` and `take_any(*)` are rejected by the parser.
- **`summarize arg_max(TimeGenerated, *) by …` is silently lossy.** It parses and
  returns rows, but only the group keys and the time: `TargetResources` and every other
  column are dropped.
- A deduplicated query with no matches returns `"data": null` instead of an empty
  table. It is still a zero, and still needs its control.

- The 10 changed raw-row queries run live, before and after, on one Microsoft 365
  administrator over 30 days:

- **Known limit.** On an account this busy, four queries still exceed the 25,000-token
  truncation on their own with genuinely distinct rows: `dir_changes_targeting`,
  `signin_detail`, `ip_prefix_sweep` and `login_failures`. Each is truncated with a
  notice rather than failing. That is why the skill now says not to run wide raw-row
  queries together.
