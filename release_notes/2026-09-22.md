## incident-investigation 1.1.1 — one incident, one account

### Why

On an MSSP grid connector every MCP tool takes an `account` argument, and the skill's
"fleet base rate" wording read as licence to compare against other customers. A run did
exactly that: a base-rate query went to a second tenant on the same connector. That is a
data-segregation breach regardless of how useful the comparison looked.

### Implementation notes

- **New "Hard rule — one incident, one account" section**, ahead of the steps. Lock
  `ACCOUNT` in step 0 and pass only that value to every call; `list_accounts` is allowed
  once, to confirm the name.
- **Account not found → no investigation.** If the requested account is not on the named
  connector, the skill stops before any search, query or rule call — no close-match guessing,
  no trying other connectors or accounts.
- "Base rate", "census", "fleet" and "campaign" are defined as **within this account**. Any
  cross-tenant context needs the user's explicit yes naming the accounts.
- Only the connector the user named is used; a call that reaches the wrong account is
  discarded and reported.
- Step 2 base rate and step 7 tuning evidence are explicitly intra-tenant. For a single
  tenant-wide actor (a service principal, a Microsoft first-party service) the in-tenant base
  rate is that actor's own history plus the directory audit at the same instant.
- Required inputs now name the connector **and** the account; if either is missing or
  ambiguous, ask.
- The chat closure ends with a data-boundary line naming the connector and account.

## incident-investigation 1.1.2 — closure report on request

### What changed

- **New step 8.** The investigation still stops at the verdict; the closure ends with a
  one-line offer to render an HTML report, built only when asked.
- **Rendered, not hand-written.** `scripts/render_closure.py` turns a closure JSON into a
  Fluency-branded, self-contained HTML page (logo embedded as a data URI, light and dark
  themes). It refuses JSON missing a required section (`title`, `lede`, `verdict`, `meta`,
  `grounds`, `negatives`, `recommendation`, `footer`) or with an unknown verdict. Field
  reference in `assets/closure_schema.md`; two worked examples in `assets/examples/`
  (multi-day admin incident, single-event incident).
- **Replaceable logo.** `--logo <image>` (PNG/JPEG/SVG/WebP/GIF) or a `"logo"` path in the
  closure JSON, resolved against the JSON's folder; `--logo` wins. The bundled
  `assets/fluency_logo.png` is the default. An unreadable or unsupported logo stops the render
  instead of silently falling back to the wrong brand.
- **Customer-facing naming.** The report never names the MCP connector. `Tenant` is the
  account's **display name** from `list_accounts` (e.g. `Contoso Ltd`, not `contoso`), used in
  the metadata grid, header tag, footer and prose; the footer boundary line reads
  "All findings: `<display name>` only."
- **Fill rules** carry the 1.1.1 boundary into the report: every figure measured in this run
  on this account only; section titles state findings; AI-assist claims quoted verbatim, then
  tested; no zero without a control (a check that could not run is written as a gap, never a
  pass); timeline times from the raw index, never summary buckets.
- **Fallback.** On an install that carries only `SKILL.md`, the skill says the renderer is
  missing and offers to fetch the package, rather than hand-writing a substitute.

### Provenance

The renderer, schema, logo and examples come from a parallel 1.3.0 branch of this skill.
They were adapted on import: the examples were **anonymised** (the originals carried real
customer names, tenants and object ids), the schema and script docstring were aligned with
the one-account rule, and 1.3.0's "report after every investigation" behaviour was dropped in
favour of report-on-request.

### Verification

- Both examples render; a closure JSON missing required sections is rejected.
- Logo override tested five ways: default, `--logo`, JSON `"logo"`, missing file (error),
  unsupported type (error).
- A real closure was rendered end to end and checked in light and dark themes at desktop and
  phone widths.
- Skill folder, staged copy and `cowork/incident-investigation.skill` scanned for tenant names,
  customer domains, people, IPs and GUIDs: clean. `scripts/validate_skills.py --worktree`
  passes.

## ingext-promql 1.0.4 — `fluency_import_*` per-source import metrics

### What changed

- **New §8 in `references/metrics_catalog.md`:** `fluency_import_count` (events) and
  `fluency_import_bytes` (bytes) received from an individual configured import source —
  syslog listener, forwarder, agent.
- **Labels:** `importSource`, `syslogSender`, `deviceType`, `eventType`, `customer`, `app`,
  `namespace`. There is **no `account` label**; tenant scope comes from which account the
  `prom_query` call targets, not from a label filter.
- **Five example queries:** rate by source, bytes by device type, daily event total, top-10
  sources, and point-in-time cumulative bytes.
- **Correction:** the catalog previously said `fluency_import_*` was not observed on live
  tenants. It is observed, and it is a distinct family — not an alias for `lake_ingress_*` or
  `platform_component_bytes`. The `lake_import_*` → `lake_ingress_*` note is kept.
- Scope counts updated in `SKILL.md` and the catalog: **nineteen counters across seven
  families** (was seventeen across six), plus the `ingext_queue_length` gauge. Added to the
  summary table.
- Sample values for `importSource` are generic (`EDGE_FW1`, `CORP-SCCM01`); no live-tenant
  source names are shipped.
