## 1.0.1 — summary timestamps are 2-minute buckets

### Implementation notes

- **`from`/`to` on a behavior summary are bucket labels, not event times.** The eventwatch
  engine buffers on a **2-minute window**, and the summary carries the start of the bucket
  the event fell into. Measured before the mechanism was confirmed: every `from`/`to` value
  across 210 samples from two tenants on two separate clusters is an exact multiple of 120,000 ms — zero seconds, even minute,
  no exceptions. Paired against the raw index, the stamp is always *early*: 03:06:00 for an
  event at 03:06:16, 08:12:00 for one at 08:13:44, 06:54:00 for one at 06:55:15. That the
  stamp precedes the event is what rules out a processing-cycle timestamp — a batch stamp
  cannot land before the record arrives.

- **The summary brackets the event and hits it on neither side.** `from` runs up to two
  minutes early; `incidentDetectionTime` runs minutes late (07:05:00 for that same 06:55:15
  event), and the AI-assist summary quotes the late one. The skill previously warned only
  about `incidentDetectionTime`; it now states the rule for both — use the summary to find
  *which* events to pull, never to say *when* they happened.

- **The cost is an inverted timeline, not a rounding error.** On the service-principal-removal
  incident the removal would have been placed at 06:54, ahead of the role removals that
  actually preceded it at 06:55:14 — reversing a four-step transaction whose sequence was
  the entire argument for the verdict. A correlation window anchored on summary time can
  also miss the very event the incident is about.

- Skill description updated to name the timestamp trap alongside the error-code, user-agent,
  duplicate-row and geolocation ones. Repackaged to `cowork/incident-investigation.skill`.

### Still open

- Whether the 2-minute buffer is fixed or configurable is not established here, and the
  rule anatomy in `eventwatch-rule` lists `timeSlices ["1d","1h","1m"]` — one minute, not
  two. Those are rule rollup windows rather than the engine's buffer, but nothing in either
  skill yet says so explicitly.


## 1.0.2 — a tuning proposal is a claim, and mine was wrong

The `scripts-c8` session measured the suppression condition this skill recommended for
`AzureAD_User_Add_Authentication_Method` and it did not survive. Correcting it is worth
more than the original advice was.

### Implementation notes

- **The recommended condition had zero discriminating power.** The skill said to suppress
  when the change is self-initiated **and** MFA was satisfied on an already-registered
  device **and** no method was deleted. Faceted over the rule's own selector, 7 days on
  that tenant: **all 212 hits were self-initiated** — `targetResources.userPrincipalName`
  and `initiatedBy.user.userPrincipalName` are the same list, same 34 users, same counts.
  Suppressing on it would have disabled the rule. The other two clauses are not expressible:
  behavior filters see only the rule's own attributes plus `key`/`keyType`/`behavior`, so
  they cannot compare two fields, reach `StrongAuthenticationPhoneAppDetail` in another
  source, or correlate across events in a window.

- **The real defect was selector over-matching, and it is not tenant-specific.** The rule
  counted every Authentication Methods event with `operationType` Add and result success —
  three events per enrolment, not one. Of 212 hits: 103 "User started security info
  registration" (ceremony start, nothing added), 55 "User registered all required security
  info" (rollup after the add is already logged), 54 "User registered security info" (the
  actual addition). 75% were not additions. Excluding the two non-add activities takes 212
  hits to 54 with every real addition still firing, and no tenant scoping or suppression.

- **Step 7 now makes tuning a tested claim, not a suggestion**, with three questions in
  order: can the engine express it, does it discriminate when faceted over the rule's own
  selector, and is the rule over-matching instead? The worked failure is written up as the
  example, because a plausible-sounding condition is exactly what gets shipped unmeasured.

- **Masking the wrong risk term gives the wrong answer.** Severity and ML boost are separate
  risks; de-boosting means masking the **ML** risk, while masking the severity zeroes the
  score. The skill previously implied the score could be tuned down via the rule itself.

- **`ruleID` in a behavior summary is a tenant-side UUID.** The Scripts repo keys rules on
  integer ids, and those are what its release registries and history track — quote both when
  handing a finding to a rule maintainer. Noted in step 7.

### Still open

- `risk_config.json` reportedly carries `ALERT_SEVERITY_HIGH = 400` and `ML_NEW_USER = 500`,
  but the observed score is 3600 on a 400 severity. Those two constants alone do not produce
  it, so the boost is not a simple sum and the arithmetic is still unexplained here. The
  skill states the operational rule (mask the ML risk, not the severity) without claiming the
  formula.


## 1.0.3 — the riskScore formula, and what tuning actually buys

`scripts-c8` derived the scoring formula from `fsbv2/risk/risk_enum.go` and, in doing so,
retracted part of what it had told us in 1.0.2. Both halves are in the skill now.

### Implementation notes

- **The formula, verified independently here against four scores from three tenants.**
  `contribution = factorScore × scopeMultiplier × appends`, where scope is global 4 /
  local 2 / none 1; the rule-level ALERT risk is appended once per behavior event capped
  at 2, ML hits once each; duplicates dropped, max 2 hits per Name per factor, only the
  first 8 hits of a factor score. Then `score = subtotal × boost`, boost being 1/2/4/8 for
  1/2/3/4 distinct dimensions (hardcoded 2.0 per dimension, product halved once above 2.1,
  not in `risk_config.json`). Reconstructing 3600, 8400 and 6400 + 4400 across three
  tenants gives 4/4 exact, and implies `ALERT_POLICY = 200` alongside the
  known `ALERT_SEVERITY_HIGH = 400` and `ML_NEW_USER = ML_NEW_ALERT = 500`.

- **The summary's `hits` array is not the append list.** It carries distinct hit *shapes*;
  the alert risk was appended once per event behind it. A naive reconstruction from `hits`
  under-counts precisely when `count > 1` — that was the one case out of four that missed
  before the per-event append was modelled.

- **Retraction carried over from 1.0.2: trimming the selector does not lower a score.**
  1.0.2 implied the `AzureAD_User_Add_Authentication_Method` fix would reduce the incidents.
  It does not. The alert term caps at two appends, so a day with 11 genuine registrations
  and a day with 2 both contribute 800; the subject actually made 11 that day, and the score is
  3600 before and after. The fix buys 212 → 54 events, truthful hit counts, and users with
  no genuine add dropping out — not a lower number.

- **Only masking the ML risk reaches the score**, because it removes the contribution *and*
  collapses the dimension multiplier: 3600 → 800. Masking the severity zeroes it instead.
  Step 7 now requires naming which lever is being proposed and what it buys.

- The closure artifact was republished (v3) with the same correction and a score
  decomposition table, having briefly carried the overstated claim in v2.

### Still open

- The dimension boost is hardcoded rather than configured, so the only tenant-level control
  over these scores is a `RiskFilter` with `riskMask`. Whether that is the intended design
  or a gap is an fsbv2 question, not a Scripts one.


## 1.0.4 — constants read from source, and where a finding stops being yours

`scripts-c8` confirmed both open items from 1.0.3 against the source, which turns two
inferences into facts and adds one ambiguity worth knowing.

### Implementation notes

- **The factor table is now read, not inferred.** From `fsbv2/risk/risk_config.json`:
  `ALERT_SEVERITY_LOW` 100, `ALERT_SEVERITY_MEDIUM` 200, `ALERT_POLICY` 200,
  `ALERT_SEVERITY_HIGH` 400, `ALERT_SEVERITY_CRITICAL` 600, and
  `ML_NEW_ALERT`/`ML_NEW_USER`/`ML_NEW_ASSET` 500 each. The `ALERT_POLICY = 200`
  derived in 1.0.3 from three scores is correct.

- **`ALERT_POLICY` and `ALERT_SEVERITY_MEDIUM` are both 200**, so they cannot be told
  apart by working backwards from a score on the alert dimension. Read the risk off the
  summary instead. This matters because `ALERT_POLICY` is the risk on many Office365
  rules, including the two that produced those scores.

- **The hits-array trap now carries its mechanism.** The scoring path calls
  `AppendHitByNames` once per behavior event with no dedupe beyond the documented caps;
  the `hitMap` behind the readable array dedupes separately — by hit name for rule-level
  risks, by value equality for `RuleHits`. The array you can read is deduplicated and
  the array that was scored is not, which is why a reconstruction under-counts exactly
  when `count > 1` and only on the alert dimension.

- **New in step 7: where a finding stops being yours.** Triage produces ticket-scoped
  findings and platform-scoped observations, and the second kind — when first-seen
  boosts, how the dimension multiplier works, what the engine buffers — is a different
  repo with a far larger blast radius, which nobody asked for. Name it as an observation
  and route it to a person. Written up because of how today went: two sessions agreed
  that the ML first-seen behaviour is worth changing, and agreement between agents is
  not authorisation. Neither session opened that thread.

### Still open

- The ML first-seen behaviour remains unraised with either fsbv2 session, deliberately,
  pending a human deciding whether it is worth pursuing and which session owns it.


## 1.0.5 — attributes are not cosmetic, and a summary count can under-report

Verifying `scripts-c8`'s shipped `CredentialChange` attributes turned up a detection gap,
and root-causing it produced the most generalisable finding of the day.

### Implementation notes

- **A summary's `count` can be lower than the number of real events.** The engine dedupes
  behavior events on a key built from `Key`, `KeyType`, `BehaviorRule` **and every attribute
  value joined together** (`eventwatchv2/dao/behavior.go`, `BehaviorEventBuffer.Check`); a
  second event with the same key inside the interval is blocked outright. Found on
  one tenant: the lake held **two** `Certificates and secrets management` events on
  2026-09-05, one per application, while the summary said `count: 1`. The sibling
  `O365_Update_Application` counted 3 of 3 on the same day because it carried the target as
  an attribute; the credential rule carried only Username / Workload / Operation /
  ResultStatus, identical across both apps. The score confirms it independently — 8400 only
  closes with one alert append.

- **Therefore: attributes are not cosmetic.** An attribute set that cannot distinguish two
  concurrent events causes one to be silently dropped — never emitted, not merely
  unreadable. "The summary omits the target" and "the rule only fired once" are frequently
  the *same defect*, and the fix for one is the fix for the other. Step 7 now says to report
  a thin attribute set as a detection gap rather than a readability complaint, because that
  framing is what gets it prioritised correctly. `scripts-c8` reproduced both directions
  under the old and new rule; the shipped change fixes the collapse without further work.

- **A base rate of 1 may be a collapse.** Step 2 now points at the raw-count cross-check
  before anything is concluded from a lone entity.

- **A correctness fix here raises scores.** Restoring the second event adds an alert append,
  taking that day from 8400 to 8800. Previously-hidden event surfacing, not escalation — but
  it reads as a regression on a score trend, so it is worth saying out loud when it happens.

- **Query-form traps, both real and both costly.** The credential `Operation` is spelled with
  an **en dash** and a **trailing space** — `Update application – Certificates and secrets
  management ` — so exact-equality matching fails on either, and the CLI's `--must` filter
  does not round-trip the en dash at all. Four working `ingext kql` forms are now in the
  skill. Also recorded: these forms apply to *schema'd* indexes; `ingext kql` returns no rows
  against `default`, which needs `ingext datalake search`.

### Still open

- `beKey` is built by concatenating attribute values in attribute order, and that order is
  not stable run to run, so dedup can also fail to collapse genuine duplicates. It errs
  toward emitting more events, which is the safe direction, but `beKey` equality is not a
  reliable duplicate test when reasoning about counts.
- The end-to-end check of the new attributes — rendered subject line and multi-app count —
  is still pending a post-20260920-2 event landing on that tenant. Both have so far been
  proved only on reconstructed events.


## 1.0.6 — the emission boundary makes the count check cheap

A precision fix on 1.0.5, from `scripts-c8`. 1.0.5 said to cross-check every summary count
against raw. That is more work than the mechanism requires.

### Implementation notes

- **The dedup runs at behavior-event emission**, before the event is buffered, so a blocked
  event never reaches a summary and the raw index — upstream — is untouched by it. The
  boundary is therefore sharp: a base rate counted from **summaries can be collapsed**, one
  counted from **raw rows cannot**. The instruction is no longer "cross-check every count"
  but "know which side of the emission boundary your number came from".

- This retroactively clears that tenant's verdict. 1.0.5 recorded a worry that its
  "not a campaign" conclusion rested on an uncross-checked base rate of 1. It did not: the
  supporting evidence was six audit rows over 30 days covering all three identifiers, which
  is a raw-side census and immune to the mechanism. The concern is withdrawn.

- Practical effect: a raw-side census — the directory audit for an activity class,
  `campaign_census.kql`, an object's full history — needs no cross-check. A
  `search_summary` count does.


## 1.0.7 — the tenant profile is shared global state

An operational hazard both this session and `scripts-c8` hit today without either
noticing at the time.

### Implementation notes

- **`ingext config use` mutates `~/.ingext/config.yaml` for every session on the machine.**
  Two sessions triaging different tenants swap targets under each other with nothing in the
  output to say so. It happened in both directions today: this session's verification
  switched the profile to one tenant while `scripts-c8` believed it was on another, and
  `scripts-c8` had earlier moved it twice more for its own queries.

- **The mitigation is per-call attribution, not before/after sampling.** `scripts-c8`
  suggested reading the profile immediately before and after a load-bearing run. Stronger
  and cheaper: read the siteURL out of the call's own debug log, which is what actually
  answered. A flip and flip-back inside one call passes a before/after check while the call
  went elsewhere.

- **`ingext_json.py` gains a `kql` mode and `--expect`.** `ingext -l debug kql` coexists with
  `--output`, so the JSON lands clean while the log still carries the siteURL. Both `kql` and
  `run` now print the site that answered and exit non-zero on a mismatch. This closes a real
  gap in this skill's own tooling: every KQL query run during today's three investigations
  went through plain `ingext kql --output`, which prints no siteURL at all, so none of them
  carried tenant proof.

- **Worst case is server-side evaluation.** `eventwatch rule_test` and `processor test`
  execute on whatever profile is current and their output does not name the cluster. A
  result you cannot attribute to a cluster is unattributed, not merely untidy — it matters
  the moment two clusters run different platform versions.

- Step 0 now states the global-mutation property, the per-call assertion, the server-side
  hazard, and the courtesy of restoring the profile and saying where you left it.

### Still open

- `scripts-c8` re-ran everything load-bearing under the restored profile and got
  byte-identical results, so nothing either session reported today needs revisiting. That was
  established retroactively, which is exactly the position the `--expect` assertion exists to
  avoid.


## 1.0.8 — server-side evaluations can be attributed after all

Correction to 1.0.7, from `scripts-c8` verifying it.

### Implementation notes

- **1.0.7 said `rule_test` and `processor test` cannot be attributed to a cluster. Wrong.**
  They accept `-l debug` like every other call, so the siteURL is available:
  `ingext -l debug eventwatch rule_test --content @rule.json --event ev.json 2>&1 | grep -a siteURL`.
  The hazard stands — their normal output names no cluster — but it now comes with a remedy
  rather than only a warning.

- **Attribution effort should not be uniform, and step 0 now says where it pays.** Datalake
  and KQL reads are self-attributing: rows carry tenant identifiers, so a wrong-cluster query
  returns nothing rather than something plausible. Server-side evaluations are the dangerous
  ones precisely because they return a confident answer with no cluster in it. That is why
  this session's exposure to today's profile collisions was nil while `scripts-c8`'s was real
  — it was running `rule_test`, and none of this session's evidence came from a call of that
  kind.


## 1.0.9 — a zero against a large scan, and relayed claims

Both from a false finding this session produced, relayed and had to retract during a
FortiGate coverage review on one provider's sites.

### Implementation notes

- **The error.** Queried `NetworkFortigateEvent` and `NetworkFortigateTraffic` with
  `where timestamp > ago(7d)` and got 0, and reported the indexes as empty since the
  Metaflow migration. Those are static Parquet schema indexes whose time column is
  `TimeGenerated`; they do not populate `timestamp`. Re-run on that site: 5,225,327 and
  353,354,170 rows over the same window. Nothing was empty and nothing was broken.

- **Step 6 gains the general trap.** The result count and the scan total sit next to each
  other and only one answers the question — `total: 24377719` with no rows means 24M were
  read and the filter matched none, which is far more often a wrong column than an absent
  fact. An absence is the one result that looks identical whether it is true or broken, so
  prove the query can return something before reporting one. The per-family time columns are
  listed explicitly: `timestamp` for Office365 and behavior, `TimeGenerated` for
  AzureSigninLogs, AzureAuditLogs and the two FortiGate Parquet indexes.

- **Step 7 gains the relay rule.** The finding was passed to the session maintaining the
  Scripts repo, which verified the repo half (the reports really do query those indexes),
  passed the tenant half through unverified, and escalated to a human as silent breakage.
  Attribution is not verification: "the other side measured X" reads as established while
  being exactly as good as X was. Verify with your own access, or label it unverified and
  say what would confirm it. Both sessions also independently misread the scan total as the
  match count while checking — the two numbers are adjacent in the output.

- **Nothing else in the review was affected.** The rule census, firing census and rule-body
  analysis come from `rule_list`, the `behavior` index and `rule_get`, none of which touch
  those indexes.


## 1.0.10 — a missing column returns null, and rules do not read the lake

Third instance today of "an absence that looks identical whether it is true or broken",
and a variant the 1.0.9 write-up did not cover. Found during a FortiGate rule design on
one provider's sites.

### Implementation notes

- **A projection over a non-existent column returns `null` for every row.** 1.0.9 covered
  the *predicate* form — a filter that cannot match returns zero. This is the *projection*
  form, and it is worse in one respect: the result set is populated, so nothing looks
  wrong. `project srcip, user, method, logdesc` on a FortiGate lockout event returned four
  nulls. Two were real; `method` and `logdesc` are simply not promoted columns in the
  `NetworkFortigateEvent` Parquet schema. The field that actually carried the source
  address — `ui` — was never projected, because a projection only returns names chosen in
  advance.

- **Defences now in step 6:** read the schema before projecting, or query the nested
  container (`_fields`, `@fortigate`) and inspect the whole object rather than a
  hand-picked list. When an expected field is null, check the column exists before
  concluding the data is absent.

- **Behavior rules read the event stream, not the lake.** Column promotion is a
  lake-schema property, so a field missing from the Parquet index can be perfectly
  available to a rule. Rule field paths must be validated against the raw `default` index.
  This is what let the lockout rule key on `@fortigate.ui` with no parser change, after
  both sessions had concluded a `msg`-text extraction was a prerequisite.

- **Cost of the error, stated precisely.** Both sessions concluded that a `msg`-text
  extraction was a prerequisite for the lockout rule, and that rule was recommended to a
  user as the higher-value of two parser candidates on that basis. The recommendation was
  wrong for about one exchange and was corrected before anything was built for it. The
  `msg` extraction was **never written**.

  It is worth not inflating this. A separate parser change, `enrichAdminLoginIP`, *was*
  written, tested and shipped the same afternoon — but it was never a prerequisite for the
  lockout rule, and its own justification (the country sub-rule and the second dimension on
  102083/102084) is untouched by this finding. No implementation was wasted. The cost was a
  misranked recommendation, not a wasted build, and the trap is worth recording on the
  smaller true cost rather than a larger false one.


## 1.0.11 — `-l debug` leaks the bearer token; attribution only needs `-l info`

A credential-exposure defect in this skill's own guidance and tooling, raised by
`scripts-c8`. Shipped in 1.0.7 and present until now.

### Implementation notes

- **`ingext -l debug` dumps the `Authorization: Bearer` header**, writing the tenant's
  API token into whatever captures the output — a transcript, a pipe, a file on disk.
  1.0.7 introduced per-call tenant attribution and told the reader to use `-l debug` for
  it, including for `eventwatch rule_test`. That guidance created the exposure it was
  meant to make safe.

- **`siteURL` is logged at INFO.** Verified: `ingext -l info` prints
  `siteURL=https://…` and contains no `Bearer` string at all. So attribution never needed
  debug in the first place. Step 0 now uses `-l info` and states why.

- **`ingext_json.py` fixed in both modes.** `kql` mode drops to `-l info` — `--output`
  already supplies the body, so debug bought nothing there. `run` mode still needs debug,
  because the response body for non-`kql` calls exists only at that level, so it now
  redacts `Authorization: Bearer …` before the log is written to disk. Verified after the
  change: `kql` log contains zero `Bearer` occurrences, `run` log contains zero raw tokens
  and one `[REDACTED]` marker, and both still return their bodies and their siteURL
  assertion.

- **Existing logs scrubbed.** 42 files written earlier in the session contained a live
  token; all were redacted in place, leaving zero raw tokens on disk.

- Reach for `-l debug` only when the response body is genuinely needed, and redact before
  the output is stored.


## 1.0.12 — customer identifiers removed from the skill and its package

Audit of the skill for customer-specific data. The `.skill` package is distributed and
installed by other people, so anything in `SKILL.md` or `scripts/` travels to whoever
installs it — one customer's tenant names would have been visible to another customer's

a lesson was lost, only the identifiers that carried no information.
