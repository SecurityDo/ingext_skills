# 2026-07-28 — the syslog family: 10 per-device setup skills (R1 resolved)

The syslog half of the connector-skills rollout (`plans/connector-skills-rollout.md`). The
2026-07-24 pass deliberately skipped the entire syslog family because **R1** — where a device
actually points its syslog — was unanswered. R1 is now resolved, so these ten shipped together.

**R1, as resolved:** the site's syslog transport is managed through MCP calls —
`syslog_get_config` to read it, `syslog_register_config` to create it (**once per site, ever**),
`syslog_update_config` to enable an additional listener on an existing config. That yields the
endpoint domain, port and protocol (TCP/UDP/TLS), and TLS sources are handed the platform CA
bundle at `https://fluency-public.s3.us-east-1.amazonaws.com/certs/ca.crt`.

Every skill is **self-contained**: it resolves the transport, installs the connector, and guides
the device side — so `customer-onboarding` routes straight to it with no `add-connector`
follow-on.

## Implementation notes

- **The device-side runbook is the deliverable.** These skills are deliberately weighted toward
  the non-Fluency half: exact menu paths, CLI blocks, which log categories are forwarded and
  where that is chosen, the save/commit step, and how to confirm on the device itself. The
  Fluency half is three tool calls; the device half is where onboarding actually fails.

- **Transport was verified per device rather than assumed** — and two working assumptions were
  wrong, which is precisely why it was verified:
  - **Meraki is not UDP-only.** MX on **MX26.1+** supports TCP and encrypted syslog (RFC 5425);
    MS/MR are UDP for now. The skill branches on firmware.
  - **SonicWall TLS is SonicOS 8 only.** SonicOS 7.0/7.1 and 6.5 expose no protocol field at all
    — UDP only. 7.2/7.3 could not be verified (the 7.3 guide 404s) and is an explicit stub.
  - Verified TLS: FortiGate (via the `tls_rfc6587` listener — see R14 below), Palo Alto (SSL,
    TLS 1.2), Cisco ASA (`secure`), Sophos Firewall, Linux/rsyslog. UDP-only: Peplink, Sophos
    UTM 9. TCP by necessity: Check Point (see R13 below).

- **`automatic-linux-rhel-syslog` is the only `automatic-*` of the batch**, because it is the only
  one whose *device* side the agent can execute. It bundles `setup-ingext-rsyslog.sh`: writes
  `/etc/rsyslog.d/10-ingext-forward.conf`, installs the CA, registers a non-514 port with SELinux
  (`syslogd_port_t`), **validates with `rsyslogd -N1` and restores the previous state rather than
  restarting on a config that does not validate**, then restarts and prints one JSON object to
  stdout with progress on stderr — the house script convention. A broken rsyslog config can stop
  a host logging entirely, so validate-then-restart-else-restore is the safety property, and the
  skill also says plainly that a fleet is a configuration-management job, not fifty SSH sessions.

- **Operational hazards surfaced rather than buried.** Cisco ASA gets a warning box *above* "What
  this creates": TCP/TLS syslog **fails closed** — Cisco's own wording is that new connections
  through the ASA are blocked when the collector is down (and since 8.3(2) a full logging queue
  does the same). `logging permit-hostdown` is ordered before the `logging host … secure` line in
  every block, and the fail-open/fail-closed tradeoff is put to the customer instead of decided
  silently. Sophos UTM 9 carries its **end-of-life (30 June 2026)** status directly under the
  title.

- **Verification uses the device's own log view as ground truth**, then a datalake row count with
  the table confirmed via `list_data_tables` (none of these templates define an index). Where the
  vendor documents a test event it is included — `logger` on Linux, `%ASA-5-111008` from any
  non-`show` command on ASA, a config change + Commit on PAN-OS. Where none exists it is stated
  as a verified absence rather than invented: PAN-OS has **no** "Send Test Log Message"; Meraki
  has no test-syslog facility; SonicWall's substitute is its documented Packet Monitor capture.

## Items discovered during the build (plan §5)

None were guessed around. Two were **answered by the Fluency team the same day** and applied
across the family; the rest remain explicit stubs in the affected skills.

### Answered and applied

- **R14 — RFC 6587 octet framing: yes, on a dedicated listener.** `syslog_get_config` reports
  **`tls_rfc6587`** and **`tls_rfc6587_port`** for exactly this, and `syslog_register_config` can
  create that listener when a site has none. **`setup-fortigate-syslog` now targets
  `tls_rfc6587`** rather than plain `syslog_tls` — FortiOS 6.0+ frames with octet counting, and a
  newline-framing listener would concatenate its messages into unusable records. The
  merged-records failure mode changed from "escalate to support with a sample" to a concrete
  "you are pointed at the wrong listener; here is the fix".

- **R13 — client certificates: not accepted.** Syslog TLS is one-way; the device verifies the
  platform and presents nothing. Applied three ways:
  - **Check Point** — Log Exporter does mutual-auth TLS *only* and has no one-way mode, so **TCP
    is now stated as the correct transport, not a compromise**, with the unencrypted tradeoff
    named and a private path offered as the answer for customers who require encryption. Its TLS
    section is retained but explicitly gated off.
  - **Palo Alto** — *unblocked*. PAN-OS's "both certificates must share a CA under client auth"
    constraint never arises, so plain one-way SSL works and the skill now says to skip the
    client certificate entirely.
  - **Sophos Firewall** — *unblocked*. Its documented `peer_verify(required-trusted)` flow (which
    assumes the receiver trusts the firewall's default CA) does not apply; the skill now says not
    to bother exporting `Default.pem`, and its TLS failure-mode row redirects to the two causes
    that actually matter (CN/SAN match and CA import).

### Settled by inspection

- **R1a — what the platform CA file actually is.** Downloaded and inspected with `openssl x509`: a
  5888-byte PEM bundle of **five public roots** (Amazon Root CA 1–4, Starfield Services Root CA
  G2). So the syslog TLS endpoint presents a **publicly trusted** certificate — many devices
  validate it with no import at all, and importing the bundle is best described as **pinning**
  trust to those roots. It is server-trust only and can never act as a client certificate, which
  is the same fact R13 confirms from the platform side. One skill draft had asserted the opposite
  (that CCADB "will not contain Fluency's platform CA"), which would have sent Meraki customers on
  an unnecessary and failing certificate detour; corrected across the family.

### Still open

- **R12 — which syslog *format* does each Fluency parser expect?** The one unresolved question for
  this family. Hit by every firewall skill: FortiGate `default` vs alternatives, PAN-OS **BSD vs
  IETF**, SonicWall **Default vs Enhanced**, Check Point `syslog` vs CEF/LEEF (plus `read-mode
  raw` vs `semi-unified`). A wrong choice lands rows that never parse — silent breakage rather
  than an obvious failure. Each skill recommends the vendor default and ships a diagnostic
  ("rows arriving but fields unparsed → try the alternate → ask Fluency"), but this is worth
  settling centrally rather than rediscovering per customer.
