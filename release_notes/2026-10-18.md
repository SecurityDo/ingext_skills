# 2026-10-18 — incident-investigation 1.2.23 → 1.2.24

Before calling an address "new" or "never used", check whether the same address has
already carried the user's mail, or a colleague's.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.2.24 | released |

## Why

An automated run escalated a password-reset ticket on an Office365-only tenant twice. It
called two addresses "never-used networks" and "attack traffic that never succeeded", and
said no other employee used them. Its address census counted sign-in rows only. Office365
sign-in rows are sparse, because one token covers hours of use. Outlook desktop rows from
the same two addresses showed that they had carried the subject's mailbox, and a
colleague's, for 4 and 7 days before the ticket. The rejected tokens were the ones the
password reset had just revoked.

Only sign-in rows give a reliable location. Exchange `REST`/`RESTSystem` rows carry
Microsoft datacenter addresses. So the fix is a check scoped to the ticket's addresses
that compares IPs only. It is not a census of every workload.

## Changes

- **New bundled query `ip_client_o365`.** For `{IPS}` over 30 days, it returns the first
  and last time each address was seen, by actor, mailbox and source. The sources are
  sign-in rows, Outlook desktop rows (`Client=MSExchangeRPC`) and OWA rows. It matches
  the IP only and never reads a location from it. It was validated and run against the
  case above, in about 95 s on a small tenant.
- **office365.md 3a, a two-step check before calling an address new:**
  1. Pre-filter with `behavior_event_search` over 30 days on the quoted IPs. It runs in
     milliseconds. If the address is already on this user, or on other users, before the
     ticket, stop.
  2. Run `ip_client_o365` only when the address is missing there or first appears at the
     ticket. The behavior index holds only a sign-in fingerprint, so a miss there proves
     nothing.
