# 2026-09-16 — new skill: azure-log-analytics-search

One new skill. `azure-log-analytics-search` queries a customer's **own** Azure Log
Analytics / Microsoft Sentinel workspace live with KQL, through the `azure_logs_*`
tools added to the tenant and grid MCP servers in ingext_remote 9.12.x. Nothing is
ingested: every call authenticates as the customer's app registration and reaches
their Azure tenant. For what the skill does and its trigger phrases, see its section
in the root `README.md`.

## Implementation notes

- **Kept distinct from `ingext-kql`.** The two are easy to conflate — same language,
  overlapping subject matter — and picking the wrong one produces a confidently wrong
  answer against the wrong data. The description, the opening section and the scope
  rules all say outright that this is not the datalake, that the table set is Azure's
  (`SigninLogs`, not `AzureSigninLogs`), and that the datalake's embedded schema KB
  must not be used to answer an Azure question.

- **No embedded schema.** Every workspace holds only what its data connectors
  populate, so discovery is live: `azure_logs_list_tables` (with `filter` — a
  Sentinel workspace can run to hundreds of entries) then `azure_logs_get_schema`
  for the handful being queried.

- **The time-range rule is the headline gotcha**, because it is inverted relative to
  our own `kql_search`: Azure ANDs the supplied range with any time predicate inside
  the query and the *narrower* wins. A query carrying `ago(7d)` run with the 24-hour
  default returns nothing and reads as "no events". The skill's rule is to omit
  `rangeFrom`/`rangeTo` whenever the query constrains time itself, and to always read
  back the echoed `timespan`.

- **`rangeFrom`/`rangeTo` are epoch milliseconds.** Seconds are accepted and land in
  January 1970 with an empty result, which is why the skill makes checking the echoed
  `timespan` for a `1970-` prefix an explicit step.

- **Functions are first-class.** On a Sentinel workspace the ASIM parsers are
  `kind: function` and are usually the better query target. `columnSource` on each
  schema says whether the columns came from workspace metadata (free, with Microsoft's
  descriptions) or from a probe (an execution, names and types only), and the skill
  spells out that an absent `columns` with a `columnsError` is *not* "returns nothing".
  Function schemas need ingext_remote 9.12.12 or later; the skill says what the older
  behaviour looks like so it is not misread as an empty workspace.

- **References.** `references/azure_kql_notes.md` covers the dialect differences,
  table-name mapping, tables vs functions and ASIM, the capitalized Kusto v1 result
  envelope, sign-in `ResultType` codes, and dynamic columns.
  `references/troubleshooting.md` covers the failure modes with their real remedies —
  notably the 403 whose documented fix (switch to the ARM endpoint) is a red herring
  for a missing workspace role assignment, and `AADSTS7000215`, where a GUID in
  `clientSecret` means the secret **ID** was pasted instead of its **value**.

- **Verification.** Every behaviour the skill asserts was exercised against a live
  customer workspace through the tenant MCP server on ingext_remote 9.12.12: the four
  tools end to end, the filter and `total` semantics, case-insensitive schema
  resolution and `notFound`, `columnSource` of both kinds plus a real `columnsError`,
  in-band validation of a bad query, the 24-hour default and the echoed `timespan`,
  and `truncated` at a small `limit`. The skill names no table or parser that is
  specific to that workspace: the ASIM guidance is deliberately a rule about
  listing them, not a list.

- **Cowork package built.** `cowork/azure-log-analytics-search.skill` — 3 files,
  archive layout matching the existing packages.
