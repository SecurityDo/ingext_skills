# 2026-07-15 — new skill: customer-onboarding (the front door for data import)

One new skill. `customer-onboarding` is the entry point a new Fluency / Ingext customer hits when
they want their data in but don't yet know which connector they need. It presents a menu of
supported applications, routes each choice to the skill that actually performs the setup, verifies
events land in the datalake, and loops back for the next source.

This is the repo's first **router** skill. Every other skill performs a procedure; this one performs
none. `SKILLS/` had fourteen skills and no front door — a customer had to already know that
CloudTrail meant `setup-aws-cloudtrail-connector`, that Defender meant `create-ingext-defender-app`
*followed by* `add-connector`, and that everything else meant `add-connector` alone. That map lived
only in the README and in whoever had read all fourteen SKILL.md files.

## Implementation notes

- **New skill `customer-onboarding` (1.0.0).** Standard `SKILL.md` + `references/` + `evals/`
  layout, `add-connector`'s interactive onboarding voice.

  - **Hybrid menu.** A curated catalog of applications with dedicated skills, plus an "anything
    else" branch that falls through to `add-connector`'s live `list_connector_templates` lookup.
    The menu stays short and readable while nothing on the platform becomes unreachable. Step 1
    calls `list_connectors` first so already-installed applications are marked rather than
    redundantly offered.

  - **The credential hand-off — the gap this actually closes.** `create-ingext-audit-app` and
    `create-ingext-defender-app` both end by producing `tenantId` / `clientId` / `clientSecret`
    "for the downstream install-application stage", but nothing carried those into `add-connector`,
    which consumes them. A human read two SKILL.md files and copied values across. The router now
    captures the three values on return and invokes `add-connector` with them in hand. `SKILL.md`
    states that `clientSecret` is never echoed back in a summary or checklist.

  - **Microsoft 365's two-path fork documented.** M365 has a customer-owned app path
    (`create-ingext-audit-app` → `add-connector`) and a hosted OAuth consent path (`add-connector`
    alone, `adminConsentEmail` only — see `add-connector` Step 7). They are not interchangeable and
    the router must ask before routing. The catalog records the auth path per application.

  - **Router discipline.** Two rules are stated explicitly in `SKILL.md`: invoke the sibling skill,
    never paraphrase its runbook (an inlined copy of a CloudFormation parameter table or an Entra
    permission list would drift silently); and if a routed-to skill isn't installed, name it, point
    at the repo, and stop that branch — never improvise IAM trust relationships or admin-consent
    grants from memory.

  - **Verification is part of onboarding.** An application is Done only when events land, not when
    the connector installs. Step 5 checks `list_connectors` state, waits out the honest per-source
    first-event latency (CloudTrail ~5 min S3 batching; O365 Management API ~30–60 min; OAuth
    connectors send nothing until the admin completes consent), then counts rows via `ingext-kql`
    against the catalog's table for that app. On failure it hands back to the sibling skill's own
    Failure modes table rather than debugging from scratch. Site-wide health defers to
    `ingext-health-monitor`.

  - **Session checklist.** Done / ⏳ Pending / ❌ Failed per application, reprinted at the end.
    `SKILL.md` calls out that silently dropping a source that installed but never delivered an event
    is the one failure mode that actually costs the customer data.

- **`references/application_catalog.md`.** The routing map, and the single file to edit when a new
  deep-dive skill lands. Per application: aliases, ordered skill route, auth path, prerequisites,
  what it hands back, datalake table, first-event latency. Seeded with the three guided applications
  and the common `add-connector` targets already aliased in that skill. The standard-application
  rows are explicitly marked as recognition aids, **not** an authoritative template list — the
  platform is the source of truth via `list_connector_templates`.

- **`AskUserQuestion`'s 4-option cap shaped Step 2.** The catalog renders as a markdown table in the
  reply (full picture, all rows visible), and the question carries only the four branches. The
  auto-added "Other" free-text absorbs a customer typing a vendor name directly, which routes
  through the "Something else" branch.

- **Evals (6).** Cold-start onboarding; the Defender credential hand-off chain; an uncatalogued
  vendor (CrowdStrike) falling through to `add-connector` rather than being declared unsupported; a
  multi-application session with the checklist; and a stalled O365 connector deferring to failure
  modes. Eval 4 is a **negative case**: "set up the AWS CloudTrail connector, bucket X in us-east-1"
  must trigger `setup-aws-cloudtrail-connector` **directly** and never present the menu — trigger
  theft from the dedicated skills is the main regression risk of adding a router, and the
  description's negative routing exists to prevent it.

- **`cowork/customer-onboarding.skill`** built from source with Python's `zipfile` (the mount blocks
  `zip`'s temp-file rename), archive root `customer-onboarding/` containing `SKILL.md`,
  `references/`, and `evals/`.

## Also in this release — `cowork/add-connector.skill` repackaged

Rebuilt from source so its archive root is `add-connector/` rather than `add-connector-v2/`, a name
no other archive used. **This was a naming fix only** — the packaged `SKILL.md` was byte-identical
to `SKILLS/add-connector/SKILL.md` (md5 `ac2d1a64…`), so despite the `-v2` root and a 05-22-2026
mtime the content was never out of date. Worth stating plainly, because the archive *looked* stale
and wasn't: anyone who installed it got the current instructions.

## Open question — two packaging conventions coexist in `cowork/`

Auditing all fifteen archives turned up a third pattern. Twelve are rooted at the skill name
(`add-connector/SKILL.md`); three — `azure-user-signin-investigation`, `ingext-health-monitor`, and
`office-user-investigation` — are packaged **flat**, with `SKILL.md` and `assets/` at the top level
and no containing directory.

These are left as-is pending an answer to: **does the installer require a root directory, or accept
both?** If it accepts both, the three are fine and repackaging them is churn (one is a 179-file
archive). If it requires a root, those three are broken today — which would matter, not least
because `customer-onboarding` defers site-health questions to `ingext-health-monitor`.

The convention asserted in these release notes ("archive root = the skill name") is prose that three
of fifteen archives contradict, so it is not itself evidence. The manual packaging process has no
consistency check to catch this class of drift; a build script would.
