# 2026-09-29 — incident-investigation 1.2.2 → 1.2.3 → 1.2.4, ingext-get-profile 1.0.0 → 1.0.1

Don't call `list_accounts` when the caller already verified the account.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.2.3 | released |
| ingext-get-profile | 1.0.1 | released |

## Why

Step 0 confirmed the target account with `list_accounts`, once. On a provider's grid
connector that call returns **every customer on the connector**, and it lands in the
run's conversation and stored trace. The Agent Portal runs this skill against one
account whose name it already knows, and may later show that trace to the account's
own users. They would see the provider's whole customer list.

The confirmation still matters when a person types the name: the grid proxy serves
the provider's own manager account for an unknown name instead of failing. The Agent
Portal now does that check server-side before the run and never shows the list to the
model.

## What changed

- **incident-investigation**
  - The hard rule no longer allows `list_accounts` unconditionally. When the caller
    supplies a verified account (the Agent Portal says so in its prompt and blocks the
    tool), the skill never calls it. Only an interactive run, where a person typed the
    name, confirms it once, and uses nothing else from the list.
  - Step 0 ("Targeting is per call") is split into those two cases.
  - The closure's `Tenant` display name comes from the caller when given, else from
    the interactive confirmation; `closure_schema.md` matches.
- **ingext-get-profile**: the same condition on its standalone confirmation.

## Verification

- `scripts/validate_skills.py --worktree` passes; both `cowork/*.skill` packages rebuilt.
- No customer identifiers added.

## Second release: incident-investigation 1.2.3 → 1.2.4

The directory-audit check is split into summary → targeted list → one operation in full.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.2.4 | released |

## Why

On an IT admin, `dir_changes_targeting.kql` (already bounded and deduplicated in 1.2.2)
returned **1,000 rows, ~790k tokens** — the row cap, with 1,576 matching rows behind it.
The agent read only the first ~25k tokens (the per-tool-result truncation), so that
check was mostly unread. Two causes:

- The query matched the subject as target **or initiator**. An admin initiates most of
  the tenant's directory changes: user updates, licences, group adds, password resets.
  Those are ordinary work, not changes made *to* the subject, which is what the check is
  for.
- `AdditionalDetails` (56%) and `TargetResources` (38%) were 94% of the bytes.

## What changed

- **New `dir_changes_summary.kql`**: counts per direction ("by subject" / "on subject")
  × activity × initiator × result, with operations (distinct CorrelationIds), first/last,
  distinct targets and IPs. Run first.
- **`dir_changes_targeting.kql` rewritten**: only changes made TO the subject by someone
  else, one row per operation, `Changes` as "property: old -> new" (values cut to 80
  characters; a removal carries the group or role in the old value), target identities
  and CorrelationId. `AdditionalDetails`, the raw `TargetResources` and object/template
  id properties are left out.
- **New `dir_changes_detail.kql`**: one operation in full, by `{CID}` (new placeholder).
- The Office365 workflow runs the three in order; "Bounded queries" gains the
  summarize-first pattern.

## Verification

| On | Query | 1.2.3 | 1.2.4 |
| --- | --- | --- | --- |
| IT admin, busy tenant | directory audit | 1,000 rows / ~790k tokens | summary 49 rows / ~1.9k + targeted 210 rows / ~17.6k |
| admin, small tenant | directory audit | 35 rows / ~75k tokens | summary 5 rows / ~0.2k + targeted 8 rows / ~1.2k |

- On the busy tenant the summary's "on subject" operations (209) match the targeted
  list (210 rows, 203 operations): `mv-expand` drops nothing.
- The detail query returns the full row for one CorrelationId.
- All 19 bundled queries parse on the engine. Both packages rebuilt; no customer
  identifiers.
