# 2026-09-30 — incident-investigation 1.2.6 → 1.2.7

Office365 fallback for tenants without the AzureAudit feed.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.2.7 | released |

## Why

The Office365 workflow's directory-change checks (`dir_changes_*`, `app_actions_audit`,
`campaign_census`) read `AzureAuditLogs`, and not every site collects that feed. Those
checks became gaps on those sites. `Office365` carries part of the same data:
its `AzureActiveDirectory` rows. How much of it was measured before it went in.

Measured on one large tenant with both feeds, fixed 5-day window:

- `Office365` `RecordType == 8` rows are Entra's **Core Directory** audit service only, and
  match `AzureAuditLogs` near 1:1 per operation (role adds 75/77, group adds 1383/1386,
  service principals 12/12). `InterSystemsId` equals `CorrelationId`.
- Absent entirely: Authentication Methods (security info), PIM, self-service password
  reset, Device Registration Service (BitLocker, LAPS, Windows Hello), Identity
  Protection, B2B invites, Terms of Use, RBAC elevate-access. Within Core Directory:
  Hard Delete, "Create application – Certificates and secrets management", and some
  licence changes (126 of 176).
- `ClientIP` / `ActorIpAddress` are empty on every directory row.
- Both feeds had the same newest event: no extra latency.

## What changed

- New `assets/queries/`: `dir_changes_summary_o365.kql`, `dir_changes_targeting_o365.kql`,
  `dir_changes_detail_o365.kql`, `campaign_census_o365.kql`. `app_actions_audit.kql` needs
  no fallback: `app_actions_o365.kql` already returns the app's `AzureActiveDirectory` rows.
- `campaign_census_o365.kql` counts users whose authentication-method list **grew or
  shrank**, not users whose method property changed: the MFA service rewrites
  `StrongAuthenticationPhoneAppDetail` at the same device count for ~340 users a day,
  against ~40 real registrations, and counting it would make every incident look like a
  rollout. The delta tracks `AzureAuditLogs` registrations (one day: 45 vs 41 users added,
  6 vs 7 removed).
- `references/workflows/office365.md`: a fallback section (query mapping, what Office365
  never has, no initiator IP, the closure's fixed gap sentence) and pointers in 3c.
- `SKILL.md`: step 2 names the census fallback; `{CID}` notes `InterSystemsId`.

## Verification

- Every new query parses (`ingext kql validate`), and each was run side by side with its
  `AzureAuditLogs` original on a 7-day window. Summary: all 6 Core Directory rows identical
  in operation count; missing only the 72 LAPS recoveries and 9 PIM self-activations the
  original also showed. Targeting: every Office365 operation id is in the original; the
  original's only extra ids are 7 "PIM activation expired". Detail: returns the operation
  by `InterSystemsId`.
- `scripts/validate_skills.py --worktree` passes; `cowork/incident-investigation.skill` rebuilt.
- No customer identifiers added.

# 2026-09-30 — incident-investigation 1.2.7 → 1.2.8

An Okta workflow. `okta_` tickets used to fall through to the generic workflow, where the
investigator writes its own queries.

## Skills updated

| Skill | Version | Status |
| --- | --- | --- |
| incident-investigation | 1.2.8 | released |

## Why

On an Okta lockout, the question that decides the recommendation is **how** the failed
sign-ins arrived. Okta records it in the request path (`debugContext.debugData.requestUri`).
Improvised queries rarely select it, and whole documents are cut before it is reached. A
password spray through Microsoft 365 **legacy authentication**
(`/app/office365/…/sso/wsfed/active`, relayed by Microsoft, no user agent, a new address
per attempt) then reads as a list of IPs to block, which cannot keep up with an address
per attempt.

## What changed

- `references/workflows/okta.md`, six checks:
  - **K1:** which path every sign-in took.
  - **K2:** did any of it succeed, including a correct legacy password that an app rule
    then refused.
  - **K3:** the same signature on other accounts, with the attempts-to-addresses ratio
    that separates a spray from a user's own stale device.
  - **K4:** what changed on the account, split by direction.
  - **K5:** what the real sign-ins look like.
  - **K6:** freshness, so a negative never reaches past the newest event.
  - **A recommendation section that orders the layers:** stop the attempts reaching Okta,
    stop the lockouts, stop the access. An Okta app sign-on rule acts after the password
    check, so it prevents use of a guessed password but never the guessing.
- **11 bundled queries**, `assets/queries/okta_*.kql`. All count Okta events by `uuid`,
  because the datalake can hold the same event more than once.
- **Routing:**
  - SKILL.md step 3 routes `okta_` to the new workflow.
  - An Office365 sign-in ticket on an Okta-federated tenant also runs it, because its
    failed passwords are in `Okta`, not `Office365`.
  - `office365.md` says the same.

## Validated

Every query was parse-validated and run unmodified against a tenant with a known legacy
authentication spray. The checks classified the attempts correctly, found targeted
accounts that a manual search over a shorter window had missed, and separated the
account's own administrative actions from changes made to it.
